Universal test observability

Every team, framework and test run
in one place.

Test Hub collects results from unit, component, integration, functional and end-to-end suites — whoever ran them, in whatever language — normalizes them into one canonical model, and shows them in one dashboard. Anything that can send an HTTP request can publish to it.

Get started REST API Source 

$ pip install test-hub
$ test-hub demo          # 5 projects, two weeks of history, real failures
$ test-hub serve         # http://127.0.0.1:8000
Two products, one dashboardA live service, and a single self-contained HTML file. The same rendering code behind two data providers.
Retries are attempts, not overwritesA rerun is recorded beside the failure it followed, which is the only reason flakiness is measurable.
No Node, no CDNHand-written CSS and JavaScript inside the wheel. Nothing is fetched from the internet — including this site.

Getting started

Install it, seed it with sample data, and have a dashboard open in about a minute.

REST API

Every endpoint, with a curl for each. The API is the product; the SDK is a convenience.

Adapters

JUnit XML and Test Hub JSON ship in the box. New formats are entry-point plugins.

Metrics

Pass rate, failure rate, duration and flakiness — the exact formulas, and what they exclude.

Security

Loopback by default, hashed tokens, entity-free XML parsing, and a CSP of default-src 'none'.

Deployment

Docker, Compose, a reverse proxy on a sub-path, backups, and what to check before exposing it.

Start where you are

You already have JUnit XML

Almost every runner can write it. Point test-hub ingest at the file, or POST it to /api/v1/imports from your pipeline.

Your framework writes nothing useful

Write Test Hub's own JSON from a twenty-line script, or publish results as they happen over the event API.

Your format deserves first-class support

Write an adapter. It is an entry-point plugin, and the two built-in adapters are registered exactly the same way.
