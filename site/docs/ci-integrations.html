Operating it

CI integrations

There is no Test Hub plugin to install. Every CI system here uses curl or the test-hub CLI against the same REST API, so the pattern transfers to whichever one you actually use.

The shape of it

Three patterns, in the order you will want them:

PatternUse it when
Publish on finishAlmost always. Three lines, works with any framework that writes JUnit XML.
One run from many shardsA matrix or parallel build, so four shards become one run rather than four.
Stream while runningThe suite takes long enough that people watch it.

First, a token

On any machine with Test Hub installed:

shell
$ test-hub token create --label ci

It prints two things. The token goes into your CI system's secret store. The hash goes into the server's TEST_HUB_API_TOKEN_HASHES. The server never sees the token, and nothing can recover it from the server if you lose it — create another and remove the old hash.

Publish when the suite finishes

GitHub Actions

yaml
      - name: Run tests
        run: pytest --junitxml=results.xml

      - name: Publish results
        if: always()
        env:
          TEST_HUB_TOKEN: ${{ secrets.TEST_HUB_TOKEN }}
          TEST_HUB_URL: https://test-hub.internal
        run: |
          curl --fail-with-body -sS -X POST "$TEST_HUB_URL/api/v1/imports" \
            -H "Authorization: Bearer $TEST_HUB_TOKEN" \
            -F "file=@results.xml" \
            -F "project=payments-api" -F "team=payments" -F "type=component" \
            -F "environment=ci" \
            -F "branch=${GITHUB_REF_NAME}" -F "commit=${GITHUB_SHA}" \
            -F "ci_provider=github-actions" \
            -F "pipeline_id=${GITHUB_RUN_ID}" \
            -F "pipeline_url=${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}"
Two lines that are not optional if: always() — without it the publish step is skipped exactly when the tests failed, which is the run you most wanted to see. And --fail-with-body — without it curl exits 0 on a 4xx, so the step goes green while nothing was published.

Jenkins

groovy
pipeline {
  agent any
  environment {
    TEST_HUB_URL   = 'https://test-hub.internal'
    TEST_HUB_TOKEN = credentials('test-hub-token')
  }
  stages {
    stage('Test') {
      // Do not let a failing suite abort before the results are published.
      steps { sh 'pytest --junitxml=results.xml || true' }
    }
  }
  post {
    always {
      sh '''
        set -eu
        curl --fail-with-body -sS -X POST "$TEST_HUB_URL/api/v1/imports" \
          -H "Authorization: Bearer $TEST_HUB_TOKEN" \
          -F "file=@results.xml" \
          -F "project=payments-api" -F "team=payments" -F "type=component" \
          -F "branch=${BRANCH_NAME:-$GIT_BRANCH}" -F "commit=${GIT_COMMIT}" \
          -F "ci_provider=jenkins" \
          -F "pipeline_id=${BUILD_NUMBER}" -F "pipeline_url=${BUILD_URL}"
      '''
    }
  }
}

set -eu matters as much as --fail-with-body: a sh step reports the status of the last command, so without -e a failing curl in the middle of a script is invisible.

Or the CLI, if Python is already there

shell
$ pip install test-hub
$ test-hub publish results.xml \
    --url https://test-hub.internal \
    --project payments-api --team payments --type component \
    --branch "$GIT_BRANCH" --commit "$GIT_COMMIT" \
    --token-env TEST_HUB_TOKEN

--token-env names the variable. The value never appears on the command line, where it would be readable in ps by anything else on the agent and captured by any step that traces its commands. There is deliberately no --token flag.

One run from many shards

A matrix job produces one report per shard. Published naively that is four runs with a quarter of the tests each, and the dashboard shows four unrelated half-red runs instead of one complete one.

Generate one run id before the shards start, and give it to every one:

yamlGitHub Actions
jobs:
  prepare:
    runs-on: ubuntu-latest
    outputs:
      run_id: ${{ steps.gen.outputs.run_id }}
    steps:
      - id: gen
        run: echo "run_id=$(uuidgen | tr 'A-Z' 'a-z')" >> "$GITHUB_OUTPUT"

  test:
    needs: prepare
    strategy:
      fail-fast: false
      matrix: { shard: [1, 2, 3, 4] }
    runs-on: ubuntu-latest
    steps:
      - run: pytest --junitxml=results.xml --shard=${{ matrix.shard }}/4
      - if: always()
        env:
          TEST_HUB_TOKEN: ${{ secrets.TEST_HUB_TOKEN }}
        run: |
          test-hub publish results.xml \
            --url https://test-hub.internal \
            --project payments-api --type component \
            --run-id "${{ needs.prepare.outputs.run_id }}" \
            --token-env TEST_HUB_TOKEN
groovyJenkins — generate once, use in every parallel branch
stage('Prepare') {
  steps {
    script {
      env.TEST_HUB_RUN_ID = sh(returnStdout: true,
        script: 'python3 -c "import uuid; print(uuid.uuid4())"').trim()
    }
  }
}

Order does not matter, and re-running a single shard is safe: its events were already applied, so they are ignored and no count moves. That is the same idempotency guarantee that makes a retried publish free.

Stream while the suite runs

Open a run, post results as they finish, close it at the end. Each call is safe to retry.

shell
RUN=$(curl --fail-with-body -sS -X POST "$HUB/api/v1/runs" \
  -H "Authorization: Bearer $TEST_HUB_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"project_key":"storefront-web","test_type":"e2e"}' | jq -r .id)

# … the suite POSTs to $HUB/api/v1/runs/$RUN/events as tests finish …

curl --fail-with-body -sS -X POST "$HUB/api/v1/runs/$RUN/finish" \
  -H "Authorization: Bearer $TEST_HUB_TOKEN" \
  -H 'content-type: application/json' -d '{}'

Results appear in every connected dashboard within a couple of seconds, with a LIVE badge on the run. A cancelled job that never reaches the close step leaves the run open, which is the honest representation: nobody told Test Hub it finished.

The Python SDK wraps this if you are writing a framework plugin; the REST API is the whole contract if you are not.

Screenshots and traces

shell
curl --fail-with-body -sS -X POST "$HUB/api/v1/runs/$RUN/artifacts" \
  -H "Authorization: Bearer $TEST_HUB_TOKEN" \
  -F "file=@test-results/failure.png" \
  -F "kind=screenshot" -F "test_id=$TEST_ID"

Content-addressed, so fifty shards uploading the same screenshot store one copy.

Things that go wrong

SymptomCause
Step is green, nothing in the dashboardcurl without --fail-with-body, or a sh script without set -e.
Results only appear when tests passMissing if: always() / publishing in post { success }, or a failing test command aborting the stage.
Four runs instead of oneThe shards did not share a --run-id.
415 unknown_formatNot JUnit XML or Test Hub JSON. GET /api/v1/adapters lists what this server accepts.
401 unauthorizedThe secret is unset — in most CI systems a missing secret expands to an empty string rather than failing.
Branch shows as HEAD or <n>/mergeOn a GitHub pull request GITHUB_REF_NAME is the merge ref; use github.head_ref. On Jenkins prefer BRANCH_NAME over GIT_BRANCH, which includes the remote.
Publish times out on a large reportRaise --timeout, and check TEST_HUB_MAX_REPORT_BYTES on the server. Gzipped reports are accepted and decompressed with their own limit.

The full worked pipelines, including scripted-pipeline and systemd variants, are in docs/ci/github-actions.md and docs/ci/jenkins.md in the repository.
