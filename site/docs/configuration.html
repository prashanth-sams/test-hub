Configuration

Test Hub has one settings object. Everything in it is readable from the environment with a TEST_HUB_ prefix, from a .env file, or from a CLI flag, and the defaults are the ones you want on a laptop: loopback only, no auth because nothing else can reach it, modest limits, data under the platform's user-data directory.

How a setting gets its value

Four layers, highest first:

  1. A CLI flag

    Flags are layered on top of everything else in exactly one function, test_hub.cli.options.settings_from_cli. Nothing else in the codebase is allowed to reorder this.

  2. An environment variable

    TEST_HUB_ plus the field name, upper-cased: TEST_HUB_MAX_REPORT_BYTES, TEST_HUB_SSE_MAX_CLIENTS. Matching is case-insensitive, so test_hub_port works too — verified.

  3. A .env file

    Read from the current working directory, not from the data directory and not from the package. A real variable beats the file: with TEST_HUB_PORT=7001 in .env, running under TEST_HUB_PORT=7002 gives 7002.

  4. The default in config.py

    Listed for every setting in the tables below.

The exception that will catch you: servesettings_from_cli treats "not None" as "supplied", and serve passes --host, --port and --log-level unconditionally — including their defaults. The consequence is that TEST_HUB_HOST, TEST_HUB_PORT and TEST_HUB_LOG_LEVEL do not reach test-hub serve at all. Running TEST_HUB_HOST=0.0.0.0 TEST_HUB_PORT=9999 test-hub serve binds 127.0.0.1:8000. Use the flags. This is why the shipped Dockerfile repeats --host 0.0.0.0 --port 8000 in its CMD even though it also sets the environment variables.

Two flags escape that because they are wired differently. --data-dir declares envvar="TEST_HUB_DATA_DIR", so Typer resolves the variable itself and the flag and the variable are genuinely the same thing. --insecure-no-auth is passed as insecure_no_auth or None, so an unset flag reads as "not supplied" and TEST_HUB_INSECURE_NO_AUTH=true gets through — which is what makes the Compose file work.

NoteUnknown TEST_HUB_* variables are ignored rather than rejected (extra="ignore"). That is what stops TEST_HUB_TOKEN — a publisher's variable, not a server setting — from colliding with the settings model. The cost is that TEST_HUB_MAX_REPORT_BYTS is silently no configuration at all, so check your spelling when a limit does not seem to apply.

List values, and the $ problem

Five settings are lists: api_tokens, api_token_hashes, cors_allow_origins, trusted_hosts and redaction_patterns. Each accepts two forms, because both are natural: a JSON array is what a configuration-management tool emits, and a comma-separated string is what a person types into a Compose file.

shellBoth parse to the same two-element list
$ export TEST_HUB_CORS_ALLOW_ORIGINS='http://a.local, http://b.local'
$ export TEST_HUB_CORS_ALLOW_ORIGINS='["http://a.local","http://b.local"]'

Surrounding whitespace is stripped from each entry and empty entries are dropped, so a trailing comma is harmless. A value that starts with [ is committed to being JSON — if it then fails to parse you get a specific complaint rather than a list containing one strange string:

output
value starts with '[' so it was read as a JSON array, but it does not parse:
Expecting value: line 1 column 2 (char 1)

In a shell

A PBKDF2 hash has four $-separated fields — pbkdf2_sha256$120000$<salt-hex>$<hash-hex> — and test-hub token create prints it inside double quotes. Pasted verbatim into bash or zsh, the shell expands $1, $5 and $0 before Test Hub ever sees the value. Here is what that actually did:

shellThe same hash, quoted two ways
$ echo "pbkdf2_sha256$120000$59752f46ca94861a1005861f439f4481$0dd92bd0f131074061bcb0f50ace158e61ac41e7847ad1c248b9380709aa9604"
pbkdf2_sha256f46ca94861a1005861f439f4481/bin/zshdd92bd0f131074061bcb0f50ace158e61ac41e7847ad1c248b9380709aa9604

$ echo 'pbkdf2_sha256$120000$59752f46ca94861a1005861f439f4481$0dd92bd0f131074061bcb0f50ace158e61ac41e7847ad1c248b9380709aa9604'
pbkdf2_sha256$120000$59752f46ca94861a1005861f439f4481$0dd92bd0f131074061bcb0f50ace158e61ac41e7847ad1c248b9380709aa9604

The first line is not a typo in this page; that /bin/zsh in the middle is $0. Use single quotes, always. The failure mode if you do not is that the server starts happily, rejects every token, and tells you the token is invalid — so you go looking at the publisher instead of at the hash.

In docker-compose

Compose does its own interpolation before the container sees anything, and it treats a single $ as the start of a variable reference. Write each literal $ as $$:

yamldocker-compose.yml
environment:
  TEST_HUB_API_TOKEN_HASHES: "pbkdf2_sha256$$120000$$SALT$$HASH"

Without the doubling, $SALT and $HASH resolve to nothing and the value silently truncates. Here is Compose 28.3.2 fed both forms of the same hash, and asked what it made of them:

outputdocker compose config
warning: The "SALT" variable is not set. Defaulting to a blank string.
warning: The "HASH" variable is not set. Defaulting to a blank string.

services:
  a:
    environment:
      DOUBLED: pbkdf2_sha256$$120000$$SALT$$HASH
      SINGLE: pbkdf2_sha256$$120000

SINGLE lost two of its four fields and kept $120000 only because a variable name cannot begin with a digit. The container gets a hash that can never verify. Note also that config re-escapes on output, which is why the correct value comes back with its $$ intact — that is what a healthy line looks like, not a doubly-escaped one. The two warnings are the only signal Compose gives you, and they name SALT and HASH, not the setting.

The same interpolation applies to an env_file: and to the .env beside the Compose file, so a hash in either of those needs $$ too. Check before you deploy:

shell
$ docker compose config | grep TEST_HUB_API_TOKEN_HASHES

Passing the hash with docker run -e needs single quotes and no doubling, because there is no Compose in that path — only your shell.

Ingestion limits

Every one of these is a ceiling on something an untrusted uploader controls. They are enforced while reading, not after — checking a Content-Length header is advisory, and reading first and measuring afterwards is precisely the denial of service the limit exists to prevent.

SettingEnvironment variableDefaultWhat it changes
max_report_bytesTEST_HUB_MAX_REPORT_BYTES 64 MiBLargest report accepted, measured before decompression. Minimum 1024. Exceeding it is a PayloadTooLargeError: HTTP 413, exit 6.
max_artifact_bytesTEST_HUB_MAX_ARTIFACT_BYTES 128 MiBLargest single artifact — a screenshot, a video, a log — attached to a run. Minimum 1024.
max_decompressed_bytesTEST_HUB_MAX_DECOMPRESSED_BYTES 512 MiBCeiling on what a gzipped upload may expand to, enforced during expansion. This is the zip-bomb guard: a few kilobytes on the wire can otherwise become gigabytes in memory.
max_text_field_bytesTEST_HUB_MAX_TEXT_FIELD_BYTES 256 KiBLongest stack trace or captured log stored per attempt. Minimum 256. Longer text is truncated and the attempt is flagged — never silently cut, because a stack trace that ends mid-frame with no indication is worse than one that says it was cut.
max_events_per_batchTEST_HUB_MAX_EVENTS_PER_BATCH 5000Events accepted in one POST /api/v1/runs/{id}/events. Minimum 1. A larger batch is rejected rather than truncated.
store_raw_reportsTEST_HUB_STORE_RAW_REPORTS trueKeep the original uploaded file as an artifact, so you can re-parse it later when an adapter improves. Turning it off saves disk and loses that. The export --input path sets it to false for its throwaway database, because nothing will ever read those back.

Security

auth_enabledTEST_HUB_AUTH_ENABLED falseRequire a bearer token on writes. Turns itself on when api_tokens or api_token_hashes is non-empty — configuring a token and forgetting the switch is not a failure mode Test Hub is willing to have.
require_auth_for_readsTEST_HUB_REQUIRE_AUTH_FOR_READS falseClose the read endpoints too. Reads are open by default even with auth on, because the common deployment is "anyone on the team may look, only CI may write". Set it when the dashboard itself is the thing you are protecting.
api_token_hashesTEST_HUB_API_TOKEN_HASHES emptyThe preferred form. A list of pbkdf2_sha256$<iterations>$<salt-hex>$<hash-hex> lines from test-hub token create or token hash. Several entries let you rotate without downtime. Read the $ section first.
api_tokensTEST_HUB_API_TOKENSempty Plaintext tokens, hashed at startup and never logged. Convenient, and it puts a live credential in your process environment and in whatever wrote it there. Prefer hashes.
insecure_no_authTEST_HUB_INSECURE_NO_AUTH falseExplicitly allow a non-loopback bind with no tokens. Warns on every start and banners the dashboard. Development only.
cors_allow_originsTEST_HUB_CORS_ALLOW_ORIGINS emptyEmpty means no CORS middleware at all — not "same-origin only": the headers are never added, and the browser's own rules apply. Set it only if a separate frontend origin must call this API from a browser. * is accepted, and warned about when the bind is not loopback.
trusted_hostsTEST_HUB_TRUSTED_HOSTSempty When non-empty, adds Starlette's TrustedHostMiddleware and rejects requests whose Host header is not in the list. The defence against Host-header poisoning behind a proxy that forwards anything.
cspTEST_HUB_CSPsee below The Content-Security-Policy header on the dashboard and the API. Setting it to an empty string removes the header entirely.
redaction_enabledTEST_HUB_REDACTION_ENABLED trueApply the patterns below to log records and to stored failure text.
redaction_patternsTEST_HUB_REDACTION_PATTERNS 9 built-in patternsEach is compiled at startup — an invalid regex fails configuration rather than silently disabling redaction. The capturing group is what gets replaced, so Authorization: Bearer <token> keeps the word Bearer and loses the token. Setting this replaces the built-in list; it does not extend it.
redaction_placeholderTEST_HUB_REDACTION_PLACEHOLDER ***REDACTED***What replaces a match.

The shipped patterns cover bearer and basic credentials, PEM private-key blocks, passwords inside postgres://-style URLs, AWS AKIA… keys, GitHub ghp_… tokens, Slack xox… tokens, JWTs, and a generic key = value rule for names like api_key, secret and password. Order matters: the scheme-specific rules run before the generic one, so the generic rule cannot capture the word Bearer and stop.

textThe default CSP, one directive per line
default-src 'none';

style-src 'self';
img-src 'self' data:;
font-src 'self';
connect-src 'self';
form-action 'none';

default-src 'none' is only keepable because the frontend has no inline scripts, no inline styles and no remote origins. If you loosen it, you are loosening it for content that originated in somebody's test output.

The non-loopback bind refusal

One rule, checked in one place — Settings.check_bind_safety(), called by serve before the socket is opened. Binding to an interface other than loopback requires authentication. There is no silent path to an open, unauthenticated Test Hub on a network.

outputtest-hub serve --host 0.0.0.0 --port 8123
error: refusing to bind 0.0.0.0:8123 with no authentication. Create a token with `test-hub token create`, set TEST_HUB_API_TOKEN_HASHES, or pass --insecure-no-auth if this really is a throwaway development host.
  host: 0.0.0.0
  port: 8123
# exit 78

78 is EX_CONFIG from sysexits.h. It is not 1, so a supervisor can tell "this is misconfigured and will never start" apart from "this crashed and might come back", and stop restarting it.

localhost, ::1 and anything in 127.0.0.0/8 count as loopback. 0.0.0.0 and :: do not — they are wildcards that include every interface, which is the case the rule exists for. A hostname that is not one of those literals is treated as non-loopback, because resolving it would make the check depend on DNS.

Three things the gate warns about instead of refusing. The first two are only reached on a non-loopback bind — the check returns early for loopback, which is why a laptop never sees them:

ConditionWarning
Non-loopback bind with insecure_no_auth AUTHENTICATION IS DISABLED and Test Hub is bound to 0.0.0.0:8877. Anyone who can reach this port can read and write every test result.
cors_allow_origins contains *, on a non-loopback bind CORS is set to '*'. Any website a user visits can read this API in their browser.
insecure_no_auth on a loopback bind --insecure-no-auth is redundant on a loopback bind and can be dropped.

The first warning is raised in two places: by serve before it binds, and by the application at startup. The second is the one that fires when the CLI is not in the path at all — someone running create_app under their own ASGI server still gets told.

The container caseA container that binds 127.0.0.1 is a container you cannot reach, so the shipped image binds 0.0.0.0 inside its own network namespace and the Compose file publishes it as "127.0.0.1:8000:8000". That loopback prefix is the entire security model of that file: written as "8000:8000", Docker publishes on every interface and inserts its own DNAT rules ahead of the host firewall, handing an unauthenticated Test Hub to the network past ufw. See Deployment.

Live updates

SettingEnvironment variableDefaultWhat it changes
sse_heartbeat_secondsTEST_HUB_SSE_HEARTBEAT_SECONDS 15.0How often a keep-alive comment is written on an idle stream, and the retry: value (in milliseconds) sent to the browser as its reconnect delay. Must be greater than zero. Lower it below any idle timeout in a proxy sitting in front.
sse_replay_bufferTEST_HUB_SSE_REPLAY_BUFFER 1000Events kept per workspace for Last-Event-ID replay. A client that reconnects within the buffer is replayed; one that has been away longer is sent an explicit resync directive telling it to refetch over REST, because a dashboard confidently showing stale numbers is a worse failure than a reload.
sse_max_clientsTEST_HUB_SSE_MAX_CLIENTS 200Concurrent stream subscribers. Minimum 1. Each holds an open connection for as long as its dashboard tab is open, so this is a bound on file descriptors as much as on memory.

The bus is in-process. That is why serve runs one Uvicorn worker: a second worker would hold a second bus, and half the connected dashboards would miss half the events. Raising sse_max_clients does not change that.

Do not set sse_replay_buffer to 0It is accepted, but it does not mean "always resync". A buffer of zero keeps nothing, so the oldest-cursor bookkeeping never advances past the first event and a reconnecting client falls through both branches: no replay, and no resync directive either. It carries on from where it left off and silently misses whatever happened while it was away — the one outcome the resync mechanism exists to prevent. Verified against 0.1.0. Any value of 1 or more behaves correctly: a buffer of 1 replays the newest event to a current client and sends resync to a stale one. Use 1 if you want the smallest working buffer.

Verified: ingesting under TEST_HUB_WORKSPACE_SLUG=acme and then under =other left two rows in workspaces and one run under each, with neither visible from the other. Nothing is lost, but nothing is visible either. Pick the slug before you put data in, and use workspace_name for anything cosmetic.

Where the data directory defaults to

default_data_dir() follows the platform convention rather than dropping a directory into the working tree, so test-hub serve run from two different projects is one Test Hub rather than two.

PlatformDefaultChosen from
macOS~/Library/Application Support/test-hub sys.platform == "darwin"
Windows%LOCALAPPDATA%\test-hub sys.platform starts with win; falls back to ~\AppData\Local\test-hub when LOCALAPPDATA is unset
Linux and everything else$XDG_DATA_HOME/test-hub falls back to ~/.local/share/test-hub

TEST_HUB_DATA_DIR short-circuits all of it, and it is read directly from the environment inside default_data_dir() rather than only through the settings model — so the override applies even to code paths that construct settings themselves.

shellWhat the defaults resolve to on macOS
$ test-hub serve
  ...
  data      /Users/you/Library/Application Support/test-hub

Inside it, test-hub.db (SQLite in WAL mode, so it is three files while the server is running) and artifacts/. Both directories are created on first use and chmod'ed to 0700; the chmod is wrapped in a suppressed OSError because Windows and some network filesystems have no such concept, and a directory that exists matters more than a mode that does not apply.

What happens when a value is wrong

Settings are validated at construction, so a bad value stops the process rather than producing a subtly wrong runtime. The bounds are real — max_report_bytes has a floor of 1024, flaky_window_runs a floor of 2, port a range of 1–65535, and log_level/log_format are closed sets.

outputTEST_HUB_LOG_LEVEL=verbose, last lines of the traceback
ValidationError: 1 validation error for Settings
log_level
  Input should be 'debug', 'info', 'warning' or 'error' [type=literal_error,
input_value='verbose', input_type=str]
Honest about the presentationThe message names the setting and the acceptable values, which is what you need. But it arrives as a Pydantic traceback and exits 1, not as the clean error: line and exit 78 that ConfigurationError produces — settings are validated before the CLI's error handler is in a position to catch them. Verified against 0.1.0. Read the last three lines and ignore the frames above them.

Two configurations worth copying

A laptop

Nothing. The defaults are loopback, unauthenticated and stored under your user-data directory, which is correct for a machine only you can reach. Set TEST_HUB_DATA_DIR to a scratch path while you experiment so demo --reset cannot touch anything you care about.

A shared server

TEST_HUB_API_TOKEN_HASHES (which turns auth on by itself), --host 0.0.0.0 behind a proxy that terminates TLS, TEST_HUB_TRUSTED_HOSTS set to the name that proxy serves, TEST_HUB_LOG_FORMAT=json, and TEST_HUB_ROOT_PATH if it lives on a sub-path. A bearer token over plain HTTP across a network is a token you have given away.
