Operating it

Security

Test Hub ingests untrusted text from test output and renders it in a browser. Almost every security decision in the product follows from that one sentence.

The threat model

Test output is attacker-influenced input. A test name, an assertion message and a stack trace all come from code that Test Hub does not control, and they end up rendered in somebody's browser, stored in a database, and written into an HTML file that gets emailed around. The classes that matter, in the order they are likely to bite:

ClassConcretely
Stored XSSA test named <script>alert(1)</script>, or a stack trace containing </script><img src=x onerror=…>.
XML entity attacksA JUnit file with a DTD: billion laughs, or an XXE reading /etc/passwd.
Resource exhaustionA 4 GB report, or a 2 KB gzip that expands to gigabytes.
Path traversalAn artifact named ../../etc/cron.d/evil.
Credential leakageA failing HTTP client printing the Authorization header it sent.
Unauthenticated exposureA Test Hub bound to 0.0.0.0 by someone who did not think about it.

Untrusted text in a browser

Three independent layers, because any one of them can be got wrong.

Nothing is written as HTML

The dashboard has no innerHTML assignment anywhere. Every value goes in through textContent or createTextNode. That is not a convention to be remembered — a test in the suite fails on any innerHTML in the frontend sources, and the fixtures include a report whose test names and stack traces are real XSS payloads, so the escaping is exercised by simply looking at the page.

A Content-Security-Policy that can afford to be strict

text
default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:;
font-src 'self'; connect-src 'self'; form-action 'none'; frame-ancestors 'none';
base-uri 'none'

No unsafe-inline, no unsafe-eval, no remote origins. This is only possible because the dashboard ships no inline scripts, no inline styles and loads nothing from a CDN. Loosening the policy to make a feature work means the feature is wrong.

The offline report's data block

This is the subtle one. The exported HTML file embeds the whole data set inside a <script> element, and HTML does not parse the contents of a script element — the only thing that can end it early is the literal string </script. So a test named </script><img src=x onerror=alert(1)> would break out of the data block and execute.

Every <, > and & in the embedded JSON is rewritten as a \uXXXX escape, along with U+2028 and U+2029 — the two characters that are legal in JSON and illegal in a JavaScript string literal. The result is still valid JSON, so JSON.parse returns the original string exactly, but it contains no sequence an HTML parser can act on.

The same class of bug bit the asset inliner: the dashboard's own source contains the string <script>alert(1)</script> in a comment explaining this escaping contract, and inlining that verbatim truncated the whole JavaScript bundle. The exporter now neutralizes those sequences and refuses to write a file that still contains one.

Artifacts are always downloads

An artifact is attacker-supplied bytes served from Test Hub's own origin. They are sent with Content-Disposition: attachment, the stored content type (never one sniffed from the bytes) and X-Content-Type-Options: nosniff. Serving an uploaded HTML file inline would hand any publisher a stored XSS on the dashboard's domain.

XML entity attacks

All XML is parsed with defusedxml: DTDs and external entities are refused, not expanded and then rejected. The difference matters — expanding first is the attack.

shell
$ test-hub ingest billion-laughs.xml --project p
error: this XML declares a DTD or entities and was refused before it was expanded.

Both a billion-laughs and an XXE fixture are in the test suite, and both assert the refusal rather than merely the absence of a crash.

Size and decompression

Every limit is enforced while reading. Checking a Content-Length header is advisory, and reading first then measuring is exactly the denial of service the limit exists to prevent.

LimitDefault
TEST_HUB_MAX_REPORT_BYTES64 MiB
TEST_HUB_MAX_ARTIFACT_BYTES128 MiB
TEST_HUB_MAX_DECOMPRESSED_BYTES512 MiB
TEST_HUB_MAX_TEXT_FIELD_BYTES256 KiB per attempt

Gzipped reports are decompressed transparently, with the expansion checked as it happens — a decompression bomb is refused mid-expansion and never lands in memory. A truncated gzip stream is reported as truncated rather than passed on as half a report. Archives (zip, tar) are not accepted at all: "which file in here is the report?" has no safe default.

Artifact paths

Artifacts are stored content-addressed — <root>/<aa>/<bb>/<sha256> — so a publisher-supplied filename never reaches the filesystem at all. The name is kept only as a label, and even then it is stripped of path separators, .., NUL and control characters, and Windows reserved device names before it goes into a Content-Disposition header.

Uploads stream to a temporary file in the same directory and are moved into place atomically, so two concurrent uploads of the same content cannot produce a torn file.

Tokens

Test Hub stores only hashes — salted PBKDF2-HMAC-SHA256, 120 000 iterations, compared in constant time. A stolen database yields a list of digests, not a list of working tokens.

PBKDF2 rather than a bare hash of a random token because nothing stops an operator setting TEST_HUB_API_TOKENS=letmein; the KDF makes that mistake expensive to exploit instead of free. A successful verification is memoized for the life of the process, so the cost is paid once per distinct token rather than once per request.

The plaintext exists exactly once, in the output of test-hub token create. It is never written to disk and never accepted as a command-line argument — an argument is visible in ps to every other user on the machine, lands in shell history, and is echoed into the log by any CI system that traces its commands. --token-env and --token-file are the supported routes.

A rejected request returns the same message whether the token was missing, malformed or simply wrong. Telling a caller which of those it was is free information for an attacker.

Network exposure

The default bind is 127.0.0.1. Binding anything else requires authentication, and the process exits 78 before opening a socket if it has none:

shell
$ test-hub serve --host 0.0.0.0
error: refusing to bind 0.0.0.0:8000 with no authentication. Create a token with
`test-hub token create`, set TEST_HUB_API_TOKEN_HASHES, or pass --insecure-no-auth
if this really is a throwaway development host.

The escape hatch exists, because a throwaway development host is a real thing, but it must be asked for explicitly and it warns on every start and banners the dashboard. CORS is off entirely by default; * is accepted and warns loudly.

Docker publishes past your firewall Publishing a port as "8000:8000" binds 0.0.0.0 on the host, and Docker inserts its own DNAT rules ahead of ufw and firewalld — so the container is reachable from the network even if the host firewall says otherwise. The shipped docker-compose.yml publishes "127.0.0.1:8000:8000", and that prefix is the entire security model of the file.

Secret redaction

Test output is one of the great accidental secret stores. Both log records and stored failure text pass through a redactor on the way in. The defaults cover:

  • Authorization: Bearer … and Basic …
  • PEM private keys
  • Database URLs with inline passwords (postgres://user:pw@host/db)
  • AWS access keys, GitHub ghp_ tokens, Slack xox… tokens
  • JWT payload and signature segments
  • Generic password=, token=, api_key= shapes

Each pattern has exactly one capturing group, and only the group is replaced — so password=hunter2 becomes password=***REDACTED*** and stays readable. Order matters: the scheme-specific rules run first, so Authorization: Bearer <token> loses the token rather than the word "Bearer".

A second line of defence, not a guarantee Redaction is pattern matching over arbitrary text. It will not catch a secret in a shape nobody anticipated. Add your own with TEST_HUB_REDACTION_PATTERNS — and note that setting it replaces the defaults, so include the ones you still want. The first line of defence is not printing secrets in test output.

What this release does not protect against

This section is the most useful one on the page. All of these are known gaps, not oversights.

GapWhat it means for you
No per-user authorizationA token is a token. Any valid token can write to any project, and there is no notion of a user, a role or an owner. Do not hand a token to someone you would not give write access to everything.
One shared workspaceEvery row carries a workspace_id from the first migration, but the open-source edition creates only default. This is not a tenancy boundary you can rely on yet.
No audit logThe event log records what happened to the data, not who did it. There is no record of which token published what.
No rate limitingA publisher with a valid token can fill the disk. Put a reverse proxy in front of an instance exposed to anything wider than a trusted network.
No encryption at restThe SQLite file and the artifact tree are plain files. Use filesystem or volume encryption if the results are sensitive.
No TLS of its ownTest Hub speaks plain HTTP. Terminate TLS in front of it — a bearer token sent over plain HTTP across a network is a token you have given away.
Reads are open by defaultEven with authentication on, reads are unauthenticated unless you set TEST_HUB_REQUIRE_AUTH_FOR_READS. The default assumes "anyone in the team may look, only CI may write".

Reporting a vulnerability

Please do not open a public issue. Use GitHub Security Advisories on the repository. Reports are acknowledged within 72 hours. SECURITY.md in the repository has the supported versions and the disclosure process.
