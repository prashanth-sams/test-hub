Python SDK

A convenience over an API designed for curl, never a requirement. Everything the SDK does is a plain HTTP request you could make yourself; it exists so a framework plugin does not have to hand-roll multipart uploads and retry logic.

You may not need this If your CI step can run curl, use the REST API directly — there is nothing here that it cannot do. The SDK earns its place inside a Python test framework, where you are already in a Python process and want to stream results as tests finish.

Install

shell
$ pip install test-hub

The SDK ships in the same package as the server. If you only want to publish, that is still the package — it is one dependency, and the server code is never imported unless you start one.

TestHubClient

python
from test_hub.sdk import TestHubClient

with TestHubClient(
    "https://test-hub.internal",
    token=os.environ["TEST_HUB_TOKEN"],
    timeout=60.0,
    verify=True,     # False only for a self-signed internal certificate
    retries=3,
) as client:
    ...

Use it as a context manager so the connection pool is closed. It is safe to keep one client for a whole test session.

ArgumentDefaultMeaning
base_urlhttp://127.0.0.1:8000The server.
tokenNoneSent as Authorization: Bearer. Read it from the environment, never hard-code it.
timeout60.0Seconds per request.
verifyTrueTLS certificate verification.
retries3See retry policy.
clientNoneBring your own httpx.Client, for proxies or custom transports.

Publishing a finished report

python
from test_hub.domain.models import RunContext

result = client.publish_report(
    "results.xml",
    project_key="payments-api",
    team="payments",
    component="checkout",
    test_type="component",          # a string is fine; the enum is not required
    trigger="push",
    context=RunContext(
        framework="pytest", language="python",
        environment="staging", branch="main", commit_sha="8f21c0d",
    ),
    tags=["nightly"],
)

print(result.adapter, result.counts.total, result.counts.pass_rate)
# junit-xml 5 50.0

Returns an ImportResult — a typed model, so result.counts.pass_rate is a float | None rather than a dict lookup. result.warnings carries anything the adapter could not represent exactly.

A file object works too, for a report you generated in memory:

python
client.publish_report(io.BytesIO(xml_bytes), project_key="p", filename="results.xml")

Making a retry free

python
client.publish_report("results.xml", project_key="p", run_id=shared_run_id)

Passing the same run_id twice applies zero events the second time and moves no count — which is how four parallel shards become one run, and why a retried CI step is safe. idempotency_key does the same at the batch level.

Streaming results as they happen

The path a framework plugin wants: open a run, report each test as it finishes, close it.

python
run = client.open_run(
    project_key="storefront-web",
    team="growth",
    test_type="e2e",
    context=RunContext(framework="Playwright", language="typescript"),
    expected_tests=len(collected),
)

client.finish_test(
    run.id,
    suite="e2e/basket.spec.ts",
    name="adds an item to the basket",
    status="passed",
    duration_ms=812,
    project_key="storefront-web",
)

finished = client.close_run(run.id)
print(finished.status, finished.counts.pass_rate)

project_key is passed to finish_test because the stable test identity is derived from it. Give it the same value you opened the run with, or the test will not join up with its own history.

Reporting a failure

python
from test_hub.domain.models import FailureDetail

client.finish_test(
    run.id, suite="e2e/checkout.spec.ts", name="recovers from a declined card",
    status="failed", duration_ms=2500, project_key="storefront-web",
    failure=FailureDetail(
        type="AssertionError",
        message="expected 402 but got 500",
        stack_trace=traceback.format_exc(),
        expected="402", actual="500",
    ),
    stdout=captured_out, stderr=captured_err, logs=captured_logs,
)

Status words are normalized, so whatever your framework calls it is fine — "Success", "FAILURE", "expected failure" all map correctly, and the original word is preserved. A word Test Hub does not recognise becomes unknown and raises a warning; it never quietly becomes a pass.

Reporting a retry

python
for attempt, outcome in enumerate(run_with_retries(test), start=1):
    client.finish_test(
        run.id, suite=test.suite, name=test.name,
        status=outcome.status, attempt_number=attempt,
        duration_ms=outcome.duration_ms, project_key="storefront-web",
    )
Increment, never overwrite A retry is a second attempt, not a correction of the first. Re-reporting attempt 1 with a different outcome loses the failure, and reporting it as a separate test inflates the count and makes the pass rate wrong. Incrementing attempt_number gives you one test, counted once, correctly marked flaky.

Artifacts

python
artifact = client.upload_artifact(
    run.id, "test-results/failure.png", kind="screenshot", test_id=test_id,
)
print(artifact.sha256, artifact.size_bytes)

Content-addressed, so uploading the same screenshot from fifty shards stores one copy.

Reading

python
client.health()                      # version, schema version, workspace id
client.overview(window_days=30)      # the portfolio view
client.get_run(run_id)               # a run with suites, tests and comparison
client.workspace_id()                # fetched once from /healthz, then cached

These return plain dictionaries rather than models: they are for scripts and assertions, and pinning them to a model would break every time a field was added.

Errors

Everything raises TestHubClientError, carrying the server's structured error so you can branch on a code rather than parse a message:

python
from test_hub.sdk import TestHubClientError

try:
    client.publish_report("notes.txt", project_key="p")
except TestHubClientError as error:
    print(error.status_code)                      # 415
    print(error.code)                             # unknown_format
    print(error.detail["installed_adapters"])     # what this server does accept

A server that cannot be reached at all raises the same type, with status_code is None and a message naming the URL.

Retry policy

Retried: connection errors, timeouts, 408, 425, 429 and 5xx. Not retried: every other 4xx, because a malformed request will be just as malformed the second time.

Backoff is exponential and capped at 8 seconds, and honours a Retry-After header when the server sends one. A retried request carries the same X-Idempotency-Key, so a timeout that actually succeeded on the server does not produce a duplicate run.

Set retries=0 to handle it yourself.

A framework plugin, end to end

pythonSketch of a pytest plugin
import os
import pytest
from test_hub.sdk import TestHubClient, TestHubClientError

PROJECT = os.environ.get("TEST_HUB_PROJECT", "unknown")


def pytest_configure(config):
    url = os.environ.get("TEST_HUB_URL")
    if not url:
        return                       # no server configured: do nothing, quietly
    config._hub = TestHubClient(url, token=os.environ.get("TEST_HUB_TOKEN"))
    config._run = config._hub.open_run(
        project_key=PROJECT, test_type="unit",
        run_id=os.environ.get("TEST_HUB_RUN_ID"),   # set by CI so shards merge
    )


@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    hub = getattr(item.config, "_hub", None)
    if hub is None or report.when != "call":
        return
    try:
        hub.finish_test(
            item.config._run.id,
            suite=str(item.path.relative_to(item.config.rootpath)),
            name=item.name,
            status=report.outcome,          # "passed" / "failed" / "skipped"
            duration_ms=int(report.duration * 1000),
            project_key=PROJECT,
        )
    except TestHubClientError:
        # Never fail somebody's test run because the dashboard is unreachable.
        pass


def pytest_sessionfinish(session):
    hub = getattr(session.config, "_hub", None)
    if hub is not None:
        try:
            hub.close_run(session.config._run.id)
        finally:
            hub.close()
Never break the build The two except blocks are the important part. Test Hub being down, slow or misconfigured must never turn a passing suite red — a reporting tool that can fail your build is a reporting tool people remove.

Computing identity offline

You do not need the SDK, or a server, to know what a test's id will be:

python
from test_hub.domain.identity import test_identity

test_identity(
    project="payments-api",
    suite_path="tests/checkout/test_authorization.py",
    test_name="test_authorizes_a_valid_card",
    class_name=None,
    params={"currency": "EUR"},
)

It is a UUIDv5 over five \x1f-separated fields in a fixed namespace, and identity_source() is public precisely so an implementation in another language can be checked against it byte for byte. See the canonical schema.
