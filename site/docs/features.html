Features

A feature list is only useful if it says what the feature costs. This one gives the reason for each decision and names the tradeoff, so you can tell in advance whether Test Hub is the shape of tool you want.

One canonical model, whatever produced the results

Test Hub does not care what language your tests are written in, what framework ran them, or what started the run. Everything that arrives is normalized into one hierarchy:

texttest_hub.domain.models
Workspace
  └── Project
        └── TestRun            one execution of a suite of tests
              ├── TestSuite    a file / class / feature grouping
              │     └── TestCase        a test's identity within the run
              │           └── TestAttempt   one execution of it (retries!)
              ├── Artifact     a file produced by the run
              └── Event        the append-only log the run was folded from

These are Pydantic models carrying a schema_version, and they are the public wire contract. The SQLAlchemy rows on disk are a separate, private thing; nothing serializes an ORM object. That separation is what lets the table layout change — a new index, a split table, PostgreSQL — without a version bump that every consumer has to react to. The full reference is on the canonical schema page.

Ten statuses, and the framework's own word beside every one

Every framework spells its outcomes differently. Test Hub stores exactly one normalized status per attempt and always keeps the original string next to it in TestAttempt.original_status.

passed failed error skipped xfailed xpassed running queued cancelled unknown

The normalization is a lookup table, not a heuristic. A word it does not recognise becomes unknown and raises a parser warning on the import; it never becomes passed by accident. The table and its exact behaviour are on the canonical schema page.

Retries are attempts, never overwrites

This is the decision the rest of the product is built on. A rerun produces a new TestAttempt with attempt_number incremented; the earlier attempt is preserved exactly as it was recorded. Nothing in Test Hub ever mutates an attempt.

Two things follow. First, flakiness is observable — a test that failed and then passed is visibly a test that failed and then passed, not a green tick. Second, a retried test does not count twice: each test contributes once, through its last attempt, and its retry history stays available beside that.

Why "last", not "best" or "worst"A test that failed and then passed on retry is green and flaky. A test that passed and then failed on a rerun is red. Both facts stay on the page; the count follows the last thing that actually happened.

Stable test identity

A test's identity has to survive being re-run, re-ordered, re-parameterized in a different order, moved to a different line and executed on another machine. If it does not, every run invents a new set of tests, and history, comparison and flakiness are all worthless.

Test Hub therefore derives a UUIDv5 from what the test is and never from when or where it ran:

Part of the identityDeliberately excluded
project keytimestamps
suite pathline numbers, file offsets
class namedurations
test nameworker / shard id, hostname
normalized parametersrun id, build number, branch

Named parameters are sorted by name, so (b=2, a=1) and (a=1, b=2) are one test. Rendered object addresses and bare UUIDs inside parametrized ids are scrubbed to stable tokens, because otherwise a framework that prints <Foo object at 0x7f3c…> into a test name invents a new test every run. The exact hashed string is documented and testable, so a publisher in any language can compute the same UUID without ever talking to the server — see the recipe.

Live updates over SSE

Results appear in the browser within a couple of seconds without a refresh. The transport is Server-Sent Events rather than WebSockets because the traffic is entirely one-way, and SSE gives three things for free that would otherwise have to be built: automatic reconnection in the browser, Last-Event-ID replay, and passage through any HTTP proxy with no upgrade handshake.

The bus keeps a bounded ring buffer per workspace. A client that reconnects inside the buffer is replayed; one that has been away longer gets an explicit resync directive telling it to refetch over REST. Silently skipping the gap would leave a dashboard confidently displaying stale numbers, which is a worse failure than a reload. The frame format and every field are on the event contract page.

Idempotent ingestion, everywhere

Repost an event, a batch or a whole report — nothing duplicates and no count moves. This is not a nicety: CI steps get retried, networks time out after the server has already committed, and a publisher that cannot retry safely is a publisher that loses data.

  • (source, event id) is unique in the store, so an individual event can only ever be applied once.
  • X-Idempotency-Key covers a whole batch.
  • POST /api/v1/runs with a run_id you chose returns the existing run instead of creating a second one.
  • The canonical JSON adapter derives event ids as a UUIDv5 over (source, run_id, sequence, type), so importing the same file twice against the same run applies zero new events.
shellThe same batch, posted twice
$ curl -sX POST "$HUB/api/v1/runs/$RUN/events" -H 'X-Idempotency-Key: batch-1' -d @events.json
{"run_id": "4ff8b164-…", "applied": 2, "ignored": 0, …}

$ curl -sX POST "$HUB/api/v1/runs/$RUN/events" -H 'X-Idempotency-Key: batch-1' -d @events.json
{"run_id": "4ff8b164-…", "applied": 0, "ignored": 2, …}

Run comparison against the previous comparable run

"47 failures" means nothing on its own. "3 newly failing, 44 still failing, 2 newly passing" means somebody broke three things and the other 44 were already broken.

Every run is compared against the previous comparable run — the same project, team, component, test type, environment and branch. That is the narrowest slice that makes the comparison honest: comparing a staging e2e run against a unit run on a feature branch would produce a delta that means nothing. The comparison names newly failing, newly passing, still failing, added and removed tests by identity, plus deltas on pass rate, duration and total.

Flaky detection, two definitions, both written down

Within a run, a test is flaky when it both failed and succeeded across its attempts in that one run. Across runs, it is flaky when it disagreed with its own recent history. Both formulas are implemented exactly once, in test_hub.domain.metrics, and nothing else in the codebase is allowed to compute one — so no two parts of the product can disagree about the same number. The formulas.

Two altitudes, kept apart on purpose

The overview answers "how is the portfolio doing" and is cheap enough to poll. The run and test pages are the engineering drill-down and are allowed to return a lot. They are separate endpoints and separate payload types, so that making the drill-down richer cannot make the front page slower.

The analytics page sits between them and pays a bounded price for it: it reads the five most recent finished runs in full — enough for "what keeps breaking" to be a pattern rather than one run's luck — caches them, because a finished run cannot change, and never mixes in a run that is still going.

Formats are plugins, including ours

Two adapters ship in the box: JUnit/xUnit XML, and Test Hub's own canonical JSON. Both are registered through the test_hub.adapters entry-point group — exactly the mechanism a third-party package uses. There is no privileged internal path, which means the plugin API is the one we ourselves have to live with.

Test Hub deliberately does not advertise support for "any JSON" or "any XML". An adapter that guesses produces silently wrong numbers, and a wrong pass rate is worse than a failed import. Unknown input returns a 415 that lists every installed adapter. Writing one.

Secure by default, loudly

Test Hub ingests untrusted text — test output routinely contains credentials, HTML and things that look like markup — and renders it in a browser. The defaults assume that:

Loopback binding

Binding anywhere else requires authentication or an explicit --insecure-no-auth that warns on every start. There is no silent path to an open Test Hub on a network.

Hashed tokens

PBKDF2-SHA256. The plaintext exists once, in the output of test-hub token create. A stolen database is a list of digests.

Entity-free XML

Parsed through defusedxml: DTDs and external entities are refused, not expanded. Billion-laughs and XXE fixtures are in the test suite.

A CSP it can actually keep

default-src 'none', because the frontend has no inline scripts, no inline styles and no remote origins for the policy to have to allow.

Bounded everything

Upload size, decompression size, per-field text length, events per batch, SSE clients, warnings per parse.

Secret redaction

Configurable patterns applied to logs and stored failure text — bearer tokens, private keys, database URLs, cloud keys, JWTs.

The full threat model, including what is explicitly out of scope, is on the security page.

No Node, no CDN, no build step

The frontend is hand-written CSS and classic (non-module) JavaScript shipped inside the wheel. Charts are inline SVG drawn by hand. This is not asceticism, it buys three specific things: the CSP can forbid remote origins outright; a Python package that needs npm to build is a packaging liability; and a dashboard that fetches nothing from the internet renders identically on an air-gapped network and cannot quietly start leaking a request to a font host.

The same rule applies to this documentation site. It loads nothing from the internet either.

Deliberately not in the first release

Named, with the extension points left in place, because a feature list that only lists features is a sales document:

  • Test authoring or manual test management.
  • Test execution and orchestration — Test Hub reads results, it does not run tests.
  • AI failure analysis.
  • SSO, SAML and SCIM.
  • Full multi-tenancy. Every row already carries a workspace_id; there is one workspace and no UI to change it.
  • Kubernetes manifests, licence enforcement, notifications and issue-tracker integrations.

Two known limits of the first release are documented rather than hidden: single-process write throughput, and an in-process SSE bus that stops one Uvicorn worker from becoming four. Where each one starts to bite.
