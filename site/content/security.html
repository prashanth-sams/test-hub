The shape of the problem

Two facts drive everything below.

Test Hub's primary input is untrusted text that it renders in a browser. A failure message is whatever the test printed: an assertion diff, an HTTP response body, a stack trace, a fragment of HTML the code under test produced, the connection string it failed to connect with. It arrives from CI, often from repositories nobody on the Test Hub side reviews, and it is stored, indexed, shown to humans, and written into exported HTML files that get attached to tickets.

The default deployment is unauthenticated and bound to loopback, and that pairing is load-bearing. There is no configuration in which Test Hub silently listens on a network with no authentication. Opening it up is a separate step that has to be taken on purpose.

ClassConcretely, in this product
Stored XSSA test legitimately named escapes <script>alert(1)</script> in the product title, or a stack trace containing </script><img src=x onerror=…>.
XML entity attacksA JUnit report with a DOCTYPE: billion laughs, or an XXE reading file:///etc/passwd from the server.
Resource exhaustionA 4 GB report, a single 40 MB text node, an upload that fills the disk.
Path traversalAn artifact named ../../../../etc/cron.d/evil, or CON.png on Windows.
Credential leakageA failing HTTP client test printing the Authorization header it sent, or a database test printing its DSN with the password in it.
Unauthenticated exposureA Test Hub on 0.0.0.0, put there by somebody who was not thinking about it.

Everything shown on this page was run against Test Hub 0.1.0. The repository's SECURITY.md is the policy — how to report something, what is in scope, what to expect. This page is the engineering companion.

Binding, and why it refuses

Settings.check_bind_safety() in src/test_hub/config.py is the single gate. serve calls it before the socket is opened, and the app calls it again in its lifespan. It refuses rather than warns:

$ test-hub serve --host 0.0.0.0 --port 8199
error: refusing to bind 0.0.0.0:8199 with no authentication. Create a token with
`test-hub token create`, set TEST_HUB_API_TOKEN_HASHES, or pass --insecure-no-auth if
this really is a throwaway development host.
  host: 0.0.0.0
  port: 8199

$ echo $?
78

78 is EX_CONFIG. A supervisor can therefore tell a misconfiguration apart from a crash and stop restarting it — which is why the systemd unit in Deployment uses Restart=on-failure and a RestartSec rather than Restart=always.

Loopback detection is ipaddress.ip_address(host).is_loopback plus the literals localhost and ::1, so the whole 127.0.0.0/8 range counts, not only 127.0.0.1.

The opt-out exists, because a throwaway development host is a real thing, but it is loud on every start and it says so twice — once from the CLI before the server comes up, once from the app itself:

07:43:39 WARNING test_hub.cli.commands.serve  AUTHENTICATION IS DISABLED and Test Hub is
    bound to 0.0.0.0:8298. Anyone who can reach this port can read and write every test result.
  Test Hub  http://localhost:8298
  dashboard http://localhost:8298/
  API docs  http://localhost:8298/api/docs
  data      /private/tmp/th-site-nn
  auth      DISABLED on a public interface
…
07:43:40 WARNING test_hub.api.app             AUTHENTICATION IS DISABLED and Test Hub is
    bound to 0.0.0.0:8298. …

Configuring any token turns authentication on by itself (Settings._auth_follows_exposure), so the failure mode of "I set a token and forgot to enable auth" does not exist. check_bind_safety() also warns, without refusing, when cors_allow_origins contains * — any website a colleague visits could then read this API from their browser.

Docker publishes past your firewall The image binds 0.0.0.0, because a container that binds 127.0.0.1 is a container you cannot reach. That is safe only because of how the port is published. Written as "8000:8000", Docker binds 0.0.0.0 on the host and inserts its own DNAT rules ahead of ufw and firewalld, so the container is reachable from the network even though the host firewall says otherwise. The shipped Compose file publishes "127.0.0.1:8000:8000", and that prefix is the entire security model of the file.

Untrusted text in a browser

Nothing is ever written as HTML

The dashboard's rule is: no innerHTML with interpolated data. Text goes in with textContent, structure is built with document.createElement. This is not left to memory — tests/test_frontend_assets.py reads every shipped JavaScript file and fails on any line that assigns innerHTML and is not a comment.

The adapters, by contrast, carry payloads through verbatim. Importing tests/fixtures/junit/html-injection.xml stores test names that read:

'escapes <script>alert(1)</script> in the product title'
'escapes </script><img src=x onerror=alert(1)> in the coupon code'
'escapes "><b> in the search box'

That is correct, and it is worth understanding why. Those are legitimate names for a suite that tests output escaping, and an adapter that mangled them would make that suite untestable — you could never see whether your own escaping worked. Escaping belongs at the point of rendering, not the point of parsing.

A Content-Security-Policy it can actually keep

Sent on every response, including the static dashboard and the OpenAPI docs, by raw-ASGI middleware in src/test_hub/api/app.py. Read off the wire:

x-content-type-options: nosniff
x-frame-options: DENY
referrer-policy: no-referrer
cross-origin-opener-policy: same-origin
permissions-policy: camera=(), microphone=(), geolocation=(), payment=()
content-security-policy: default-src 'none'; script-src 'self'; style-src 'self';
  img-src 'self' data:; font-src 'self'; connect-src 'self'; form-action 'none';
  frame-ancestors 'none'; base-uri 'none'

No unsafe-inline, no unsafe-eval, no remote origin. That policy is only possible because the frontend ships no inline script, no inline style and loads nothing from a CDN — which is the security half of the no-Node decision. If you ever find yourself loosening the CSP to make a feature work, the feature is wrong.

The middleware is raw ASGI rather than Starlette's BaseHTTPMiddleware for a specific reason: the latter buffers responses, which would defeat the Server-Sent Events endpoint entirely.

No data is embedded in the page

The dashboard is served as static files and asks the API for everything, so there is no document into which a test name is ever interpolated. That removes a whole class of bug rather than defending against it: the byte sequence </script in a stack trace is just text inside a JSON response, and the response is parsed by JSON.parse, never by an HTML parser.

Test Hub used to ship an offline HTML export that embedded its entire data set inside a <script> element, which needed careful escaping on the way in — that export was removed (ADR-0003), and the escaping problem went with it.

What remains is the rule inside the browser: no innerHTML with interpolated data. tests/test_frontend_assets.py fails the build if any dashboard file assigns innerHTML, writes an inline event handler, or reaches for eval. The fixture suite includes a test named <script>alert(1)</script>, which renders as those characters everywhere it appears.

Artifacts are always downloads

An artifact is attacker-supplied content served from Test Hub's own origin. Rendering it inline would hand any publisher a stored XSS on the dashboard's domain. Downloads are therefore always an attachment, always the content type that was stored rather than one sniffed from the bytes, and always nosniff:

HTTP/1.1 200 OK
content-disposition: attachment; filename="____etccron.devil"
content-type: image/png
x-content-type-options: nosniff

XML entity attacks

All XML parsing goes through defusedxml.ElementTree.iterparse. DTDs, entity declarations and external references are refused before anything is expanded — the distinction matters, because expanding first is the attack. Two fixtures keep it that way, and both produce the same refusal:

$ curl -s -X POST $HUB/api/v1/imports -H "Authorization: Bearer $TOK" \
    -F file=@tests/fixtures/junit/billion-laughs.xml -F project=sec
{"error":"adapter_error","message":"this XML declares a DTD or entities and was refused
before it was expanded. Entity expansion is how an 'XML bomb' turns a 200-byte upload into
gigabytes of memory, and how an XXE reads files off the server, so Test Hub never processes
it. Re-export the report without a DOCTYPE.","detail":{"reason":"DTDForbidden"}}

xxe.xml contains <!ENTITY xxe SYSTEM "file:///etc/passwd"> and a second entity pointing at an external host, referenced from a <failure> message and body. Neither is resolved: the DOCTYPE is rejected before the document body is read at all.

The refusal is categorical. A report with a legitimate DOCTYPE — there is no such thing in practice for JUnit XML — is also refused. Refusing a DOCTYPE outright is far easier to reason about, and to test, than allowing one and trying to constrain what it may do.

The contributor rulexml.etree, lxml and minidom must not appear in an import statement anywhere under src/. There is no trusted XML input here, so there is no exception for "internal" files. defusedxml is a hard runtime dependency in pyproject.toml rather than an extra for exactly this reason. If you are writing an XML adapter, see Adapters.

Size and decompression limits

Every limit is enforced while streaming, never after buffering. Checking Content-Length is advisory — a client can lie — and reading a file first and measuring it afterwards is precisely the denial of service the limit exists to prevent. read_bounded() in src/test_hub/service/imports.py counts bytes as they arrive and aborts the moment the count is exceeded; FilesystemArtifactStore.put() does the same and unlinks its partial temp file on the way out.

SettingDefaultGuards
TEST_HUB_MAX_REPORT_BYTES64 MiBThe uploaded report, before any decompression.
TEST_HUB_MAX_DECOMPRESSED_BYTES512 MiBWhat a compressed upload may expand to.
TEST_HUB_MAX_ARTIFACT_BYTES128 MiBOne attached artifact.
TEST_HUB_MAX_TEXT_FIELD_BYTES256 KiBOne stack trace or log body. Longer text is truncated and the attempt is flagged, never silently cut.

$ curl -s -X POST $HUB/api/v1/imports -F file=@tests/fixtures/junit/simple.xml -F project=p
{"error":"payload_too_large","message":"report exceeds the 2048 byte limit
(TEST_HUB_MAX_REPORT_BYTES); split the upload or raise the limit","detail":{"limit_bytes":2048}}

That is a 413, and it arrives after 2049 bytes have been read, not after 2496. The WarningCollector in src/test_hub/adapters/base.py applies the same idea to the response: 500 warnings maximum, then a count of what was dropped, so a pathological file produces a bounded reply rather than a megabyte of JSON.

Two honest gaps First, max_decompressed_bytes is defined and validated, but neither built-in adapter decompresses anything — a .gz or .zip upload is not accepted at all — so today that setting is a promise to a future adapter rather than an active control. Do not plan around gzipped uploads working. Second, the report is read into memory as a bounded BytesIO, because auto-detection has to rewind the stream; with the default limit that is up to 64 MiB per concurrent import. If you raise TEST_HUB_MAX_REPORT_BYTES, raise it knowing that.

Artifact paths

In src/test_hub/storage/artifacts.py, the only value ever allowed to become a path is a validated digest:

_SHA256_RE = re.compile(r"^[0-9a-f]{64}$")

Blobs live at <root>/<aa>/<bb>/<sha256>. A SHA-256 hex digest cannot contain a separator, a dot segment, a colon, a drive letter or a non-ASCII byte, so the name a publisher supplied never touches the filesystem. It is a database column and a Content-Disposition value, which makes it a display problem rather than a filesystem one.

Uploads stream into artifacts/.incoming/<uuid>.part, are chmodded 0600, and are moved into place with Path.replace, so a reader never sees a partial file and two concurrent uploads of the same bytes cannot tear one. If the digest is already on disk the temp file is simply unlinked — rewriting a good file with an identical one would briefly unlink it for readers for no benefit.

The name is still cleaned, in two layers with deliberately different behaviour:

LayerBehaviour
service.runs.safe_artifact_name()A best-effort repair, on the upload path. Strips separators, NULs, control characters and quotes; replaces ..; prefixes a Windows device name with _; truncates at 255.
storage.artifacts.sanitize_artifact_name()A refusal, in the store. A separator, a .., a NUL or a device name is a ValidationError, not a rewrite.

The store refuses rather than repairs because a store that silently turned ../../etc/passwd into passwd would hand the next component a name its author never wrote, and make the guarantee impossible to test. The upload path repairs first, so the API answers 201 with a mangled label rather than 422 — losing a screenshot because somebody's filename was odd is the wrong trade:

$ curl -sX POST "$HUB/api/v1/runs/$RUN/artifacts" \
    -F 'file=@shot.png;filename=../../../../etc/cron.d/evil'
"name": "____etccron.devil"

$ curl -sX POST "$HUB/api/v1/runs/$RUN/artifacts" -F 'file=@shot.png;filename=CON.png'
"name": "_CON.png"

Ugly, and safe, and it is the label only — in both cases the bytes went to artifacts/e9/01/e90137d3…, addressed by their own digest.

Blobs are content-addressed rather than run-scoped, so an unreferenced blob is left on disk when the row that pointed at it rolls back. It is deduplicated and harmless, and deleting it would be wrong the moment two runs share it. There is no garbage collector in this release — see the gaps below.

Tokens

src/test_hub/api/security.py. Only hashes are stored, in the form pbkdf2_sha256$<iterations>$<salt-hex>$<hash-hex>: 120 000 iterations of PBKDF2-HMAC-SHA256 with a 16-byte salt, compared with hmac.compare_digest. A stolen database is a list of digests.

A KDF rather than a bare SHA-256 is a deliberate choice for a specific mistake. The tokens Test Hub generates carry 256 bits of entropy and a plain digest would be perfectly adequate for them — but nothing stops an operator setting TEST_HUB_API_TOKENS=letmein. PBKDF2 makes that expensive to exploit instead of free. To keep 120 000 iterations off the request path, a successful verification is memoized for the life of the process against a SHA-256 fingerprint of the presented token, so the KDF runs once per distinct token rather than once per request; the rejection set is capped at 4096 entries so a flood of bad tokens cannot grow the process without limit.

$ test-hub token create --label ci
  Token (shown once — copy it now)
  ths_o1a4z1Gw9tA…RWDBku0

  Configure the server with the hash, not the token:
  export TEST_HUB_API_TOKEN_HASHES="pbkdf2_sha256$120000$4f6db8b48873e1f3611aa19789ebb7ec$1f13…d214"

  Publishers use the token itself:
  export TEST_HUB_TOKEN="ths_o1a4z1Gw9tA…RWDBku0"   # label: ci
  test-hub publish results.xml --url https://… --project p --token-env TEST_HUB_TOKEN

  Test Hub keeps only the hash. Nothing can recover this token from the server.

The ths_ prefix costs four characters and buys recognition by a secret scanner and by a human reading a log.

A token is never accepted as a command-line argument. There is no --token flag anywhere; test-hub publish takes --token-env or --token-file. argv is world-readable in ps to every other user on the machine, it lands in shell history, and CI systems routinely echo the command they are about to run.

Both header forms are the same token and the same check. X-API-Key exists because several CI systems make it awkward to set an Authorization header on a generic HTTP step:

$ curl -s -o /dev/null -w '%{http_code}\n' -X POST $HUB/api/v1/imports \
    -H "Authorization: Bearer $TOK" -F file=@results.xml -F project=p
201
$ curl -s -o /dev/null -w '%{http_code}\n' -X POST $HUB/api/v1/imports \
    -H "X-API-Key: $TOK" -F file=@results.xml -F project=p
201
$ curl -s -X POST $HUB/api/v1/imports -F file=@results.xml -F project=p
{"error":"unauthorized","message":"a valid bearer token is required; send it as
`Authorization: Bearer <token>` or `X-API-Key: <token>`"}

X-API-Key is not a weaker credential, but it is a more dangerous name: an intermediary is far more likely to log a header called X-API-Key verbatim than one called Authorization, which most proxies and log pipelines already know to redact. Prefer Bearer where you have the choice.

A missing, a malformed and a wrong token all produce the same 401 and the same message. Which of the three it was is free information for an attacker.

Rotation is additive. TEST_HUB_API_TOKEN_HASHES is a list, so add the new hash, roll the publishers, then remove the old one: no downtime and no window in which both are invalid. Both forms are accepted from the environment —

$ TEST_HUB_API_TOKEN_HASHES='pbkdf2_sha256$120000$aa$bb,pbkdf2_sha256$120000$cc$dd' \
    python -c "from test_hub.config import Settings; s=Settings(); print(s.api_token_hashes, s.auth_enabled)"
['pbkdf2_sha256$120000$aa$bb', 'pbkdf2_sha256$120000$cc$dd'] True

— and a JSON array works identically. Note the second value in that output: auth_enabled turned itself on because a hash was configured.

A token cannot be revoked from inside Test Hub There is no token store, no test-hub token revoke and no expiry. Revocation means editing TEST_HUB_API_TOKEN_HASHES and restarting the process. Plan your rotation around a restart, and keep the list short enough that you know what every entry is for.

Secret redaction

Test output is one of the great accidental secret stores. A failing HTTP client test prints the header it sent; a failing database test prints the URL it dialled; a CI job that dumps its environment on failure prints all of it. Test Hub then stores that text, indexes it, shows it in a browser, and writes it into an exported file that gets attached to a ticket.

Redactor in src/test_hub/logging.py is applied on the way in: to log records through a filter installed on Test Hub's handler, and to the failure text, stdout, stderr, logs and skip reason of every attempt as it is folded into a row (_on_test_finished and _failure_json in src/test_hub/storage/repositories.py). Redacted-in means the secret is not in the database, not in the API response and not in the export — rather than merely hidden in one view.

Each pattern must have exactly one capturing group, and only the group is replaced, so the key stays readable and the failure stays diagnosable. Publishing a report whose <failure> body and <system-out> contain real-looking credentials, then reading it straight back out of the API:

Request headers: Authorization: ***REDACTED*** ***REDACTED***
DSN: postgresql://app:***REDACTED***@db.internal:5432/app
config: api_key=***REDACTED***
AWS_ACCESS_KEY_ID=AKIA***REDACTED***
password=***REDACTED***

DEFAULT_REDACTION_PATTERNS in src/test_hub/config.py covers Bearer and Basic credentials, PEM private-key blocks, database URLs with an inline password (postgres, postgresql, mysql, mongodb, redis, amqp), AWS access key ids, GitHub ghp_ tokens, Slack xox* tokens, JWTs, and a generic key=value rule for api_key, apikey, access_key, token, secret, password, passwd, pwd, authorization, auth_token, private_key and client_secret.

Order matters, and the first line above shows why it also over-fires slightly. The scheme-specific rules run before the generic ones so that Authorization: Bearer <token> loses the token rather than the word "Bearer" — but the generic authorization: rule then runs anyway and takes the word "Bearer" too. The result is more aggressive than the source comment predicts, and no less safe.

Adding your own patterns

Every organisation has one secret shape the defaults have never seen. TEST_HUB_REDACTION_PATTERNS replaces the defaults rather than extending them, so include the ones you still want.

$ TEST_HUB_REDACTION_PATTERNS='(?i)\bacme_([A-Za-z0-9]+)' test-hub serve
The trap: a comma inside a pattern List-valued settings accept both a,b,c and a JSON array. The comma-separated form splits on every comma — including the one in a {8,64} quantifier — and the halves do not compile: 
$ TEST_HUB_REDACTION_PATTERNS='(?i)tok_([A-Za-z0-9]{8,64})' \
    python -c "from test_hub.config import Settings; Settings()"
ValidationError: 1 validation error for Settings
redaction_patterns
  Value error, invalid redaction pattern '(?i)tok_([A-Za-z0-9]{8':
  missing ), unterminated subpattern at position 8
Use the JSON-array form for any pattern containing a comma: 
$ TEST_HUB_REDACTION_PATTERNS='["(?i)tok_([A-Za-z0-9]{8,64})"]' python -c "
from test_hub.config import Settings; from test_hub.logging import Redactor
print(Redactor(Settings().redaction_patterns).redact('tok_ABCDEFGHIJKL rest'))"
tok_***REDACTED*** rest
The failure is loud — the process refuses to start, which is the right way round — but the message names the regex rather than the comma, so it is worth knowing in advance. A pattern with no capturing group is silently ignored by Redactor rather than applied, so make sure yours has one, and test it against a real failing test before you trust it.

TEST_HUB_REDACTION_ENABLED=false turns the whole thing off. There is one legitimate reason to do that — you have an external scrubber in front of the ingest path — and several bad ones.

The honest limitation Redaction is regular expressions over arbitrary text. It is a strong second line of defence and it is not a guarantee. A base64 blob with no surrounding keyword, a secret split across two lines, a bespoke token format — these get through. Do not treat Test Hub as a place secrets cannot reach. Treat it as a system that reduces the damage when they do, and fix the leak at the test.

What this release does not protect against

This is the most useful section on the page. None of the following is a vulnerability; all of it is missing, on purpose, in 0.1.0, and a report about any of it will be closed with a pointer back here.

There is no authorization, only authentication

A token is a token. Every valid token can read everything and write everything: every project, every team, every run. A token you gave to a contractor's pipeline to publish one project's results can read the whole workspace and can post results attributed to any project it likes. There is no per-project scope, no read-only token, no service account and no ownership check anywhere in the codebase. AuthorizationError (403) exists in the error taxonomy in src/test_hub/errors.py and is never raised from anywhere in src/. If some results must not be visible to some publishers, run a second Test Hub.

Related, and worth stating separately: publisher identity is not verified either. A run's project_key, team, branch, commit and pipeline_url are whatever the publisher typed. Nothing checks that the token used belongs to that project, that the branch exists, or that the CI job is real. Anyone with a token can publish a green run for payments-api that never ran.

There is one workspace, and it is not a tenancy boundary

Every row carries workspace_id from the first migration — so the column never has to be added to a populated events table later — but the open-source edition creates exactly one workspace, derives its id from the slug, and offers no way to create or select another. require_read and require_write do not consider the workspace at all. Treat the schema column as future-proofing, not as isolation.

There is no audit log

Nothing records which token wrote which run, when, or from where. The events table records source — a publisher-supplied string that anyone can set to anything — and received_at. Uvicorn's access log is off by default (it duplicates Test Hub's own logging and is noisy in a terminal that is also showing test output), and it would not carry an identity anyway. If you need to know who did what, put a reverse proxy in front and keep its log; that is also the only place you will get a client IP.

There is no rate limiting

No per-token quota, no per-IP throttle, no concurrency cap on imports. A publisher stuck in a retry loop is limited only by the size caps above and by SQLite's single-writer ceiling — which under load means everyone else's imports queue behind it. If the port is reachable by anything you do not control, put a rate limit in the proxy.

And the rest, plainly

GapWhat it means for you
No retention, expiry or deletionNo endpoint deletes a run, a project or an artifact; nothing ages data out; there is no artifact garbage collector, so a blob whose rows rolled back stays on disk forever. Storage grows monotonically. Plan a volume, or plan to rm the data directory.

Verifying a deployment

Five commands, run from a machine that is not the server. If the first one returns 201, stop and re-read Binding.

# 1. Auth is on and writes are closed.
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://test-hub.internal/api/v1/runs \
  -H 'content-type: application/json' -d '{"project_key":"probe"}'      # expect 401

# 2. TLS terminates in front, and the security headers survived the proxy.
curl -sI https://test-hub.internal/ | grep -Ei 'content-security-policy|x-frame|nosniff'

# 3. Entity expansion is refused.
printf '<?xml version="1.0"?><!DOCTYPE t [<!ENTITY x SYSTEM "file:///etc/passwd">]><testsuites/>' \
  > /tmp/xxe.xml
curl -s -X POST https://test-hub.internal/api/v1/imports -H "Authorization: Bearer $TOK" \
  -F file=@/tmp/xxe.xml -F project=probe                               # expect DTDForbidden

# 4. Reads are as open, or as closed, as you intended.
curl -s -o /dev/null -w '%{http_code}\n' https://test-hub.internal/api/v1/runs

# 5. Your own secret shapes are redacted before storage. Publish a report whose failure
#    text carries a dummy credential in your format, then read it back:
curl -s "https://test-hub.internal/api/v1/runs/$RUN" | grep -c 'REDACTED'

Step 2 is worth repeating after every proxy change. Do not add security headers at the proxy: Test Hub sends its own on every response, and a second, weaker set from the proxy is how a restrictive CSP quietly becomes a permissive one.

Reporting a vulnerability

Privately, through GitHub Security Advisories on the repository — not a public issue, not a pull request, not a discussion thread. That form is private between you and the maintainers, gives somewhere to work on a fix before it is visible, and can issue a CVE and credit you when it is published.

Include the version, how it is deployed, and what an attacker can concretely do. Test Hub's blast radius depends heavily on who can reach the port, so "any CI job that can POST a report can read every other team's results" is a very different report from "a user who can already edit the config can crash the server". A crafted report file is the ideal reproducer, since that is the main untrusted input — cut it down and strip anything of yours out of it.

The commitments — 72 hours to acknowledge, 7 days to an initial assessment, 30 days targeted for a high-severity fix, coordinated disclosure, and a safe-harbour statement — are in SECURITY.md in the repository, which is the authoritative version of this section.
