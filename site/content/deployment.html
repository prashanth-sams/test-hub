What you are actually running

A single Python process serving both the API and the dashboard on one port, writing to a directory. No database server unless you choose PostgreSQL, no cache, no queue, no separate web server.

/var/lib/test-hub/
├── test-hub.db          the database
├── test-hub.db-wal      the write-ahead log — part of the database
├── test-hub.db-shm      the shared-memory index — part of the database
└── artifacts/
    ├── .incoming/       partial uploads; safe to delete when nothing is running
    └── aa/bb/<sha256>   content-addressed blobs
One worker There is no --workers flag, and adding one would be a bug. The live-update bus is in-process: two workers means two buses, and half the connected dashboards would miss half the events. When one process is no longer enough, the fix is a shared bus behind the EventBus protocol, not more workers.

Docker

$ docker build -t test-hub .
$ docker run --rm -p 127.0.0.1:8000:8000 \
    -v test-hub-data:/data \
    -e TEST_HUB_INSECURE_NO_AUTH=true \
    test-hub

The image is multi-stage: the first builds a wheel from the checkout, the second installs only that wheel. The runtime image therefore contains exactly what pip install test-hub would give a stranger, which means the image doubles as a continuous test that the wheel is installable.

It runs as uid 10001 (fixed and high, so a bind-mounted host directory can be chowned to a number that does not change between rebuilds), declares /data as a volume, and has a healthcheck that uses Python's urllib rather than curl, which the slim base does not have.

Why a bare docker run exits 78

The image binds 0.0.0.0, because a container that binds 127.0.0.1 is a container you cannot reach. Test Hub refuses a non-loopback bind with no authentication, so it exits 78 with a message telling you what to do. That is deliberate. Pick one:

  1. Real deployment — configure token hashes

    $ test-hub token create --label ci    # on any machine with Test Hub
$ docker run … -e TEST_HUB_API_TOKEN_HASHES='pbkdf2_sha256$120000$<salt>$<hash>' test-hub

    Quote it — those $ are literal. Pass the hash, never the token, and never bake either into an image: a layer is readable by anyone who can pull the tag and survives every docker rmi.

  2. Local poking about — opt out explicitly

    $ docker run … -e TEST_HUB_INSECURE_NO_AUTH=true test-hub

    Only ever combined with a port published to loopback, as the Compose file does.

Docker Compose

The shipped docker-compose.yml works on http://127.0.0.1:8000 after docker compose up -d, with a named volume so results survive down and up again.

services:
  test-hub:
    build: .
    image: test-hub:local
    restart: unless-stopped
    ports:
      - "127.0.0.1:8000:8000"      # the prefix is the security model
    environment:
      TEST_HUB_INSECURE_NO_AUTH: "true"   # safe ONLY because of the line above
      TEST_HUB_LOG_FORMAT: "json"
    volumes:
      - test-hub-data:/data
    read_only: true
    tmpfs: [ "/tmp:size=64m" ]
    security_opt: [ "no-new-privileges:true" ]

volumes:
  test-hub-data:
    name: test-hub-data
The $$ trap Compose interpolates $ as a variable reference. A hash pasted verbatim becomes pbkdf2_sha256$120000 — Compose resolves $SALT and $HASH to nothing and silently truncates it. The server then rejects every token with a message about the token, and you go looking in the wrong place. Write $$ for each literal $, in the Compose file, in .env and in anything named by env_file:. Verify before you deploy: 
$ docker compose config | grep TEST_HUB_API_TOKEN_HASHES
which re-escapes on output — you should see four $$-separated fields.

For a real deployment: delete TEST_HUB_INSECURE_NO_AUTH, add TEST_HUB_API_TOKEN_HASHES, and change the port to "8000:8000" only once something in front of it terminates TLS.

Run, not just read The image and both Compose setups — SQLite on its own, and PostgreSQL with the override below — have been built and brought up healthy, including forty concurrent imports against the PostgreSQL stack and a database restart that Test Hub recovered from by itself.

Choosing a database

SQLite is the default and needs nothing: a file in the data directory. It lets one writer in at a time, so CI jobs that finish together queue behind each other. PostgreSQL lets writes to different runs proceed in parallel and only makes writes to the same run take turns. Nothing else changes — the API, the CLI, the dashboard and the adapters are identical — and the schema is created on first start either way.

SQLite (default)PostgreSQL
Set upNothingA server and TEST_HUB_DATABASE_URL
Concurrent publishersOne write at a time, database-wide Parallel across runs; one run's writes take turns
Readers vs writersNever block each other (WAL) Never block each other (MVCC)
BackupsSQLite's .backup, plus artifacts pg_dump, plus artifacts

With Docker

The image already contains the PostgreSQL driver. Layer the override file on the Compose file; it adds a PostgreSQL container that publishes no port and points Test Hub at it. The password is required, and reaches Test Hub as PGPASSWORD rather than inside the URL, so it never shows up in the banner or the logs.

$ echo "TEST_HUB_POSTGRES_PASSWORD=$(openssl rand -hex 24)" >> .env
$ docker compose -f docker-compose.yml -f docker-compose.postgres.yml up -d
$ docker compose -f docker-compose.yml -f docker-compose.postgres.yml exec test-hub test-hub db check
  database  postgresql+psycopg://test_hub@postgres:5432/test_hub
  server    PostgreSQL 17.11
  schema    0003_postgresql_bigint (up to date)
  ready

Add COMPOSE_FILE=docker-compose.yml:docker-compose.postgres.yml to the same .env to make it the default for that directory.

Without Docker

$ pip install "test-hub[postgres]"
$ export TEST_HUB_DATABASE_URL='postgresql://test_hub:PASSWORD@db.internal:5432/test_hub'
$ test-hub db check
$ test-hub serve

Test Hub needs one database and a role that owns it, and creates its own tables. postgres:// and postgresql:// both work. The password can be in the URL (percent-encoded) or left out of it for PGPASSWORD or ~/.pgpass to supply; --database-url refuses one, for the same reason tokens are never arguments.

What PostgreSQL does not change Artifacts still live on the filesystem under TEST_HUB_DATA_DIR, so the data volume and its backup are still required. It is still one Test Hub process: the live-update bus is in-process. And switching an existing install starts with an empty database — runs already in SQLite are not copied across.

systemd

[Unit]
Description=Test Hub
After=network-online.target

[Service]
Type=exec
User=test-hub
Environment=TEST_HUB_DATA_DIR=/var/lib/test-hub
Environment=TEST_HUB_HOST=127.0.0.1
EnvironmentFile=/etc/test-hub/tokens.env
ExecStart=/opt/test-hub/.venv/bin/test-hub serve
Restart=on-failure
RestartSec=5s
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/var/lib/test-hub
PrivateTmp=true

[Install]
WantedBy=multi-user.target

/etc/test-hub/tokens.env holds one line — TEST_HUB_API_TOKEN_HASHES=pbkdf2_sha256$… — mode 0600, owned by root. No $$ doubling here: systemd's EnvironmentFile does not interpolate. That trap is Compose's alone.

Restart=on-failure and not Restart=always: a configuration error exits 78, and a supervisor that restarts a misconfiguration forever hides it.

Behind a reverse proxy

location / {
    proxy_pass         http://127.0.0.1:8000;
    proxy_set_header   Host $host;
    proxy_set_header   X-Forwarded-Proto $scheme;

    # Without this, nginx buffers the response and the live stream arrives
    # all at once — at the end. Test Hub already sends X-Accel-Buffering: no,
    # which nginx honours, but say it explicitly: it is the single most common
    # reason a dashboard sits on "Connecting".
    proxy_buffering    off;
    proxy_read_timeout 1h;    # an SSE connection is meant to stay open
}

Serving from a sub-path? Set TEST_HUB_ROOT_PATH=/test-hub, or the dashboard's own links point at the wrong place.

Terminate TLS at the proxy. Test Hub speaks plain HTTP, and a bearer token sent over plain HTTP across a network is a token you have given away.

Backups

Do not copy a live .db file The database is three files — .db, .db-wal, .db-shm — and copying only the first while the service is running gives you a database missing everything in the write-ahead log. Use SQLite's own backup, which is consistent against a running writer:
$ sqlite3 /var/lib/test-hub/test-hub.db ".backup '/backups/test-hub-$(date +%F).db'"
$ tar czf /backups/artifacts-$(date +%F).tgz -C /var/lib/test-hub artifacts

Or stop the service and copy all three files together. From a Docker volume:

$ docker run --rm -v test-hub-data:/data -v "$PWD:/backup" \
    busybox tar czf /backup/test-hub-data.tgz /data

Artifacts are content-addressed and never rewritten, so an incremental file-level backup of artifacts/ is efficient. .incoming/ holds partial uploads and never needs backing up.

On PostgreSQL, pg_dump takes a consistent snapshot of a live database, so the three-file trap does not exist — but the artifacts are still files and still need the tarball:

$ docker compose -f docker-compose.yml -f docker-compose.postgres.yml exec -T postgres \
    pg_dump -U test_hub -Fc test_hub > test-hub-$(date +%F).dump

Upgrades

$ pip install --upgrade test-hub
$ systemctl restart test-hub

Migrations run automatically on start — a user who upgrades should not have to know that Alembic exists. Back up first anyway; migrations are reversible in the test suite, not in your incident.

test-hub db check shows which database is in use and its schema revision, and exits 1 when migrations are pending; test-hub db upgrade applies them as a deliberate step. On PostgreSQL, migrations take an advisory lock, so two instances starting at once do not race to create the schema.

Every migration has a working downgrade, and CI asserts that the migrated schema matches the ORM exactly, so a model added without a migration fails there rather than in your production.

Capacity

Size is driven by captured output, not by test counts. A run of a few thousand tests with no logs is small; one test with a 200 KiB stack trace is not. Text fields are capped at TEST_HUB_MAX_TEXT_FIELD_BYTES and artifacts are deduplicated by SHA-256, so fifty shards uploading the same screenshot store one copy.

The real ceiling is write throughput: SQLite serializes writers, so concurrent publishers queue. That is correct rather than fast, and it is documented rather than hidden — read transactions were deliberately made not to take the write lock so that a long read or a dashboard poll cannot stall a publisher. When the queue becomes the problem, switch to PostgreSQL: writes to different runs then proceed in parallel. The next ceiling after that is the one process itself.

Changing the distribution name

If PyPI rejects test-hub as confusable with an existing project, one script rewrites exactly the name field in pyproject.toml and nothing else:

$ python tools/set_dist_name.py my-test-hub

It validates the new name against PEP 508 and prints a before/after diff. The import package (test_hub) and the console script (test-hub) are unaffected — only the name people type after pip install changes.
