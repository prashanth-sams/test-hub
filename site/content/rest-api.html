All endpoints are versioned under /api/v1. /healthz deliberately is not: it is infrastructure, and a container healthcheck should not need updating when the API version moves.

The machine-readable contract is served by the running instance: /api/openapi.json, with browsable documentation at /api/docs and /api/redoc.

Authentication

Off by default, because the default bind is loopback. It turns itself on as soon as any token is configured. Then every write needs one:

curl -H "Authorization: Bearer $TEST_HUB_TOKEN" …
curl -H "X-API-Key: $TEST_HUB_TOKEN" …          # same token, same check

X-API-Key is accepted because a surprising number of CI systems make it awkward to set an Authorization header on a generic HTTP step.

Reads stay open even with authentication on — the common deployment is "anyone in the team may look, only CI may write". Set TEST_HUB_REQUIRE_AUTH_FOR_READS=true to close them too.

Errors

Every failing endpoint returns the same shape, so a client needs exactly one error parser:

{
  "error": "unknown_format",
  "message": "no installed adapter recognised this file",
  "detail": { "installed_adapters": [ … ] }
}
StatuserrorMeans
401unauthorizedMissing, malformed or wrong token. The message is identical for all three on purpose.
403forbiddenAuthenticated but not allowed.
404not_foundNo such run, test or artifact.
409conflictA write contradicted one that already landed.
413payload_too_largeOver a configured size limit.
415unknown_formatNo adapter recognised the input. detail lists every installed one.
422validation_error, adapter_errorThe body did not match the schema, or the format was recognised but unparseable.

Idempotency

Every write is idempotent, twice over: at the event level through a UNIQUE(source, event_id) constraint, and at the batch level through an optional X-Idempotency-Key header. Reposting returns applied: 0 and moves no count. Retry freely — CI steps get retried, and a network timeout after the server already committed is a normal Tuesday.

GET /healthz

Cheap enough for a container healthcheck every ten seconds, and it touches the database — a Test Hub that cannot read its own store is not healthy, however well it serves HTTP. Unauthenticated, and contains no secrets, so it is safe to paste into an issue.

$ curl -s localhost:8000/healthz
{
    "status": "ok",
    "version": "0.1.0",
    "schema_version": 1,
    "database": "ok",
    "workspace_id": "b037a4b3-53f8-5326-a5d5-f5fad3c31052",
    "live_subscribers": 0,
    "time": "2026-09-09T03:44:29.301538Z"
}

workspace_id is here because a publisher cannot invent it and events carry it — the Python SDK fetches it from this endpoint once and caches it.

POST /api/v1/imports

Upload a finished report. Multipart rather than JSON because that is what curl -F, requests and every CI plugin already know how to send, and because it lets the file stream instead of being base64'd into a string.

curl -X POST http://localhost:8000/api/v1/imports \
  -H "Authorization: Bearer $TEST_HUB_TOKEN" \
  -F "file=@results.xml" \
  -F "project=payments-api" \
  -F "team=payments" \
  -F "component=checkout" \
  -F "type=component" \
  -F "environment=staging" \
  -F "branch=main" \
  -F "commit=8f21c0d"
FieldMeaning
fileRequired. The report. Gzipped files are decompressed transparently.
projectRequired. A report file does not carry a project key, so it cannot be guessed.
team, component, nameOwnership and a display name.
type, triggerTest type and what caused the run.
environment, branch, commitWhere and from what.
framework, languageFree text.
pipeline_id, pipeline_url, ci_providerA link back to the build.
tagsComma-separated.
run_idImport into an existing run. How sharded runs merge.
formatForce an adapter by name; always beats detection.

GET /api/v1/adapters

What this server can parse. Worth calling before an import fails — the same list appears in the body of a 415.

POST /api/v1/runs

Open a run to publish into. Idempotent on run_id: re-posting the same id returns the existing run rather than erroring, so a retried CI step does not fail because its first attempt already announced the run.

$ curl -sX POST localhost:8000/api/v1/runs \
    -H 'content-type: application/json' \
    -d '{"project_key":"payments-api","test_type":"e2e","team":"payments"}'
{
  "id": "3f95291c-7cdb-4c06-811b-2b0840cedee2",
  "project_key": "payments-api",
  "team": "payments",
  "test_type": "e2e",
  "status": "running",
  "is_live": true,
  "schema_version": 1
}

Send "started": false to open it as queued instead.

POST /api/v1/runs/{run_id}/events

Append results as they happen. The body is {"events": [ … ]} — CloudEvents envelopes, documented in the event contract.

curl -X POST "localhost:8000/api/v1/runs/$RUN/events" \
  -H 'content-type: application/json' \
  -H "X-Idempotency-Key: batch-1" \
  -d @events.json
{ "run_id": "…", "applied": 1, "ignored": 0, "created_run": false,
  "counts": { … }, "status": "running" }

Post it again and you get {"applied": 0, "ignored": 1} with the counts unchanged. Set "sequence": 0 on every event to have the server allocate a contiguous block; send your own monotonic numbers if you want gap detection, which you probably do for a long-running suite.

POST /api/v1/runs/{run_id}/finish

curl -X POST "localhost:8000/api/v1/runs/$RUN/finish" \
  -H 'content-type: application/json' -d '{}'

An empty body is the normal case. The final status is folded from the attempts that actually arrived, not taken from the request — a publisher's own totals drift the moment anything is retried. status in the body is honoured only for cancelled, which cannot be derived: a cancelled run looks exactly like one that stopped reporting.

POST /api/v1/runs/{run_id}/artifacts

curl -X POST "localhost:8000/api/v1/runs/$RUN/artifacts" \
  -F "file=@failure.png" -F "kind=screenshot" -F "test_id=$TEST_ID"

kind is one of screenshot, video, log, trace, report, coverage, raw_report, other. Storage is content-addressed, so uploading the same bytes from fifty shards stores one copy.

GET /api/v1/runs/{run_id}/artifacts lists them; GET /api/v1/artifacts/{artifact_id} downloads one — always as an attachment, with the stored content type and nosniff, because an artifact is attacker-supplied content on Test Hub's own origin.

GET /api/v1/overview

The portfolio answer: counts over a window, per-project health, live runs, recent runs, a trend series, and the worst offenders. Bounded by design — the trend is capped at 60 buckets whatever the window, so a year is 53 points rather than 366 — which makes it cheap enough to poll.

curl -s "localhost:8000/api/v1/overview?window_days=30&team=payments"

window_days accepts 1–365. Note total_runs (inside the window) and total_runs_all_time: when the first is zero and the second is not, every run is older than the window, and the dashboard says so rather than showing an empty state that looks like an empty installation.

GET /api/v1/runs

$ curl -s "localhost:8000/api/v1/runs?limit=1"
{
  "total": 17,
  "limit": 1,
  "offset": 0,
  "runs": [ { "id": "3f95291c-…", "project_key": "payments-api",
              "team": "payments", "status": "running",
              "counts": { "total": 0, "pass_rate": null, … } } ]
}

pass_rate: null means nothing executed — render it as an em dash, not as 0%. See Metrics.

Filters

The same parameters work here and on /overview, so a dashboard can carry a user's selection between them without translating. Each accepts a repeated parameter or a comma-separated list: ?project=a&project=b and ?project=a,b are equivalent.

ParameterFilters on
project, team, componentOwnership.
typeTest type.
environment, branchRun context.
statusRun status.
tagUser-defined tags.
searchFree text over run name, branch, commit and tags.
livetrue for runs that are queued or running.
limit, offsetPaging. limit is 1–500, default 50.

GET /api/v1/facets returns the distinct values available for each of these, which is what fills the dashboard's dropdowns.

GET /api/v1/runs/{run_id}

The engineering drill-down, and allowed to be large: the run, its suites with folded counts, every test with every attempt, its artifacts, and a comparison against the previous comparable run — same project, team, component, test type, environment and branch, which is the narrowest slice that makes the comparison honest.

The comparison carries pass_rate_delta, duration_delta_ms, total_delta and the newly_failing, newly_passing, still_failing, added and removed test-id sets. It is null when there is no comparable predecessor. Pass ?compare=false to skip the work.

GET /api/v1/tests/{test_id}

One stable test identity across runs: its latest result with all attempts, its history, flake_rate, failure_rate and average_duration_ms. ?history= accepts 1–200, default 30.

The id is the stable identity from the canonical schema — the same value in every run that executed the test, which is what makes history and flakiness possible at all.

GET /api/v1/projects

Every project in the workspace, with its key, name, default team and tags.

GET /api/v1/events/stream

Server-Sent Events. One-way, so SSE rather than WebSockets: automatic browser reconnection, Last-Event-ID replay and plain HTTP proxying, all for free.

$ curl -N localhost:8000/api/v1/events/stream
retry: 15000

event: hello
id: 42
data: {"workspace_id":"b037a4b3-…","replaying":false}

event: test-hub
id: 43
data: {"event":{"specversion":"1.0","type":"test.finished", … },"received_at":"…"}

: heartbeat
FrameMeaning
helloSent on connect. replaying says whether a Last-Event-ID was honoured.
test-hubAn applied event, as a full CloudEvent.
resyncYou have been away longer than the replay buffer, or you were too slow to drain. Refetch over REST.
: heartbeatA comment frame. It carries no id:, so it cannot advance your cursor past an event you have not seen.

id: is a bus cursor, not the CloudEvent's own id — a replayed event legitimately keeps its identity, so using that as the resume token would be ambiguous. Browsers send Last-Event-ID automatically on reconnect; a hand-written client should send the last id: it saw.

If the stream never delivers The most common cause is a reverse proxy buffering the response. Test Hub sends X-Accel-Buffering: no, but nginx needs proxy_buffering off; said explicitly — see Deployment.
