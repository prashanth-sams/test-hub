The protocol, and where the seam is

Everything Test Hub can read arrives through one interface, and it produces domain events — nothing else. It is a Protocol, so there is no base class you are obliged to inherit and no registration ceremony beyond a single entry point:

class ReportAdapter(Protocol):
    name: str

    def detect(self, stream: IO[bytes], filename: str | None, content_type: str | None) -> float: ...
    def parse(self, stream: IO[bytes], context: ParseContext) -> Iterable[DomainEvent]: ...

The seam is deliberately narrow, and the narrowness is what buys two things. An adapter is unit-testable against a fixture file with no server, no database and no event loop — the test suite further down runs in 0.07 seconds. And the file-import path and the live-publishing path share every line of code after the adapter returns, so a bug in folding or a change to how flakiness is counted cannot apply to one and not the other.

name must be unique across installed adapters and stable over time. It is stored on every run the adapter parsed, shown in the CLI and the API, and is what --format <name> selects. Renaming it later orphans that history.

BaseAdapter, if you want the boring parts written

test_hub.adapters.base.BaseAdapter supplies a stream sniffer that rewinds, the extension and content-type half of detection, and a describe() that feeds test-hub formats and GET /api/v1/adapters. Because ReportAdapter is structural, inheriting is a convenience and never a requirement — a plain class with the two methods is a perfectly good adapter.

Class attributeWhat it is used for
display_nameThe human name in test-hub formats and the adapters endpoint.
descriptionOne line, shown in the same two places and inside the 415 that lists what the server accepts.
extensionsLowercase and dotted, e.g. (".hopper.json", ".hopper"). Contributes 0.3 through hint_score().
content_typesMIME types, matched on the part before the ;. Also 0.3.
priorityTie-break when two adapters return the same score. Higher wins. testhub-json is 100, junit-xml is 50.

Detection, and what each score actually means

detect returns a confidence in [0.0, 1.0]. The registry asks every installed adapter in name order, rewinding the stream between each one, and keeps the highest score at or above MIN_CONFIDENCE, which is 0.3. Ties break on priority and then on name, so two adapters that both answer 0.9 resolve identically on every machine and in every process rather than according to whichever entry point importlib.metadata happened to yield first.

ScoreWhat it meansExample
0.0Definitely not mine. Return this rather than raising.The stream starts with < and your format is JSON.
0.3The filename extension or the content type fits, and nothing else was checked. This is the floor for selection: a file can be chosen on its name alone, but only when nothing claims it harder.results.hopper whose content could not be read.
0.6The content sniffs right — the root element or the required top-level keys are present.A JSON object carrying both a run object and a tests array.
0.9The content is unmistakably yours: a namespace, a generator tag, a marker key.A <testsuites> root, or a top-level "hopper": key.
1.0The content declares itself as yours. Reserve this for a real discriminator."kind": "test-hub-report".

--format on the CLI, or the format form field over REST, skips detection entirely and is reported with a detection_confidence of 1.0, because nothing was guessed. An explicit format wins even when the content plainly looks like something else: you asked for a specific parser and are entitled to that parser's error message rather than a silent substitution.

$ test-hub ingest results.hopper.json --project checkout-service --format junit-xml

  error: this file is not well-formed XML: not well-formed (invalid token): line 1, column 0
    reason: ParseError
A wart worth knowingThe CLI prints adapter  hopper (detected, 100% confident) in both cases, because it renders the same detection_confidence field either way. The word “detected” is not evidence that detection ran; a confidence of exactly 1.0 is either a self-declaring document or an explicit --format.

Three rules for detect

  • Never raise. Return 0.0. A detector that throws is caught, logged at warning level and scored 0.0 anyway, but the log line is noise nobody needs.
  • Read a few kilobytes, not the file. BaseAdapter.sniff(stream) reads SNIFF_BYTES (8192) and rewinds. The registry rewinds between adapters too, so you are not obliged to be tidy — but an adapter that reads 200 MB to make up its mind makes every import on the server slow, including the ones it loses.
  • Never claim “any JSON” or “any XML”. This is the rule with teeth, and it has its own section below.

Why an adapter must not claim arbitrary JSON or XML

An adapter that answers 0.6 for every JSON object will swallow coverage reports, ESLint output and half of somebody's package.json. Each of those then arrives as a run with a plausible-looking pass rate that is silently wrong, and a wrong pass rate on a dashboard is worse than an import that failed, because nobody goes looking for it. Require a discriminator your format actually has.

Test Hub holds itself to this. testhub-json refuses a JSON document with no kind key even though it has already read the whole thing, and unknown input produces a 415 whose body is the list of installed adapters:

$ curl -s -w '\nHTTP %{http_code}\n' -X POST http://127.0.0.1:8000/api/v1/imports \
    -F "file=@results.tap" -F "project=demo"

{"error":"unknown_format","message":"no installed adapter recognised this input
 (filename='results.tap', content_type='application/octet-stream').
Installed adapters:
  junit-xml        .xml, .junit, .junit.xml JUnit/xUnit XML from pytest, Surefire, Gradle, Jest, Playwright and friends.
  testhub-json     .json                  Test Hub's own report and raw event JSON (kind: test-hub-report/-events).
Pass --format <name> to skip detection and force one of these.", "detail": {...}}
HTTP 415

There is a second refusal that reads much like the first and comes from somewhere else entirely. When an adapter does claim a file — on its extension, or on a shape heuristic — and then cannot parse it, you get a 422 from that adapter rather than a 415 from the registry. A .json file with no kind takes this path, because testhub-json scores 0.3 on the extension alone:

{"error":"adapter_error","message":"this is JSON, but not a Test Hub document: the
 top-level object must carry \"kind\": \"test-hub-report\" or \"kind\":
 \"test-hub-events\". Found kind=None.","detail":{"kind":null,"adapter":"testhub-json"}}
HTTP 422

Both are refusals and neither is a guess. The distinction matters when you are writing a client: 415 means “install an adapter or pass --format”, 422 means “the right adapter looked at your file and it is wrong”.

ParseContext

Everything an adapter needs that is not in the file — the metadata a human supplied on the command line or in the REST request:

@dataclass(slots=True)
class ParseContext:
    workspace_id: uuid.UUID
    project_key: str
    run_id: uuid.UUID
    name: str | None
    team: str | None
    component: str | None
    test_type: TestType
    trigger: TriggerType
    context: RunContext
    tags: list[str]
    metadata: dict[str, Any]
    source: str                  # default "urn:test-hub:import"
    filename: str | None
    max_text_bytes: int          # default 256 KiB; mirrors TEST_HUB_MAX_TEXT_FIELD_BYTES
    warnings: WarningCollector

    def next_sequence(self) -> int: ...

Merge what the file knows with what the context says, and where the two conflict, the context wins. The person typing --environment staging has more information than a report exported three hours ago on another machine. Only workspace_id and project_key are required; every other field has a default.

Call context.next_sequence() for every event rather than counting yourself. Events emitted by nested generators then still come out strictly increasing, and a sub-parser handed the same context cannot restart the numbering at 1.

max_text_bytes is there so that an adapter never builds a 40 MB string it is about to have truncated. Respect it when you concatenate captured output.

WarningCollector: warn rather than approximate

The contract with the user is one sentence: anything you cannot represent exactly becomes a warning, not an exception and not a silent approximation. A warning travels in the ImportResult, is stored on the run, is printed by the CLI and is returned by the API. It is how “your report claimed 40 tests and I found 19” reaches a human.

context.warnings.add(
    "unknown_status",
    f"hopper outcome {word!r} has no canonical equivalent; recorded as unknown",
    location="checkout/pay",
)
context.warnings.info("synthesized_timestamps", "the report had no timestamp; using import time")

add() takes a stable code that consumers match on, a message truncated at 512 characters, an optional location, a severity of warning (the default) or info, and any further keyword arguments, which land in detail. The collector is bounded at 500 warnings, then counts what it drops and appends a single warnings_truncated note — a pathological file must still produce a bounded response.

Here is what four different warnings look like coming out of one deliberately awkward report:

  imported run 126f68ff-fd60-439d-8fa7-041e3feb1703
  adapter   testhub-json (detected, 100% confident)
  project   warn-demo
  3 tests  2 passed  66.7% pass

  4 parser warning(s):
    naive_timestamp [run]: the report contains timestamps with no UTC offset; they are read as UTC
    unknown_enum [run]: TestType 'chaos' is not a value Test Hub knows; using other
    unknown_status [tests[0]]: status 'wobbly' is not a word Test Hub knows; recorded as unknown
    attempt_renumbered [s]: attempt numbers [3] for 'b' were not 1..n; they were re-sequenced in the order given

Codes the built-in adapters already use are worth reusing rather than inventing near-synonyms for: unknown_status, unknown_enum, counts_mismatch, naive_timestamp, synthesized_timestamps, attempt_renumbered, invalid_slug, text_truncated, suite_output_lifted, status_disagrees, missing_test_name, workspace_override. The full field list is on the canonical schema page.

Derive identity through test_hub.domain.identity

Never invent test or suite ids, and never carry them from the file unless the file's ids are themselves derived the same way.

from test_hub.domain.identity import suite_id, test_identity

suite = suite_id(project=context.project_key, suite_path="checkout/cart")
test = test_identity(
    project=context.project_key,
    suite_path="checkout/cart",
    test_name="adds an item",
    class_name=None,
    params={"currency": "EUR"},
)

Both are UUIDv5 in a fixed namespace, computed from what the test is and never from when or where it ran. That is not tidiness. It is the entire reason GET /api/v1/tests/{id} has a history to show. Hash a line number and every run invents a fresh set of tests: nothing compares, nothing trends, and no test is ever flaky because no test ever appears twice.

You may omit test_id from a test.finished payload entirely and let the server derive it from the identity components you did supply. That is usually the right choice — one implementation, no drift. The exact hashed string, the normalization rules and the excluded fields are on the canonical schema page.

A retry is a new attempt, never an overwrite

Emit a second test.finished for the same test_id with attempt_number incremented. Nothing in Test Hub ever updates an attempt's outcome with a later one, because attempt 1 failing and attempt 2 passing is the entire observable definition of a flaky test, and an UPDATE erases it.

The awkward part is formats that nest earlier attempts inside the final one. Maven Surefire writes a retried test as one <testcase>:

<testcase name="settlesBatchWithinSla" classname="com.example.ledger.SettlementIT" time="9.204">
  <flakyFailure message="settlement took 11.4s, SLA is 10s" type="org.opentest4j.AssertionFailedError">…</flakyFailure>
  <flakyFailure message="settlement took 10.7s, SLA is 10s" type="org.opentest4j.AssertionFailedError">…</flakyFailure>
  <system-out>batch=BATCH-88421 rows=12044 elapsed=9.2s</system-out>
</testcase>

flakyFailure and flakyError mean “this failed, then a rerun passed”, so the <testcase>'s own absent outcome is the pass. rerunFailure and rerunError mean “the rerun failed too”, so its own <failure> is the final word. Either way the nested elements are the earlier attempts and the element's own outcome is the last one. Importing the fixture above and reading the attempts back out of the store shows what that produces:

name                      attempt  status   original_status
------------------------  -------  -------  ---------------
archivesSettledBatches          1  passed
rejectsUnbalancedJournal        1  failed   rerunfailure
rejectsUnbalancedJournal        2  error    rerunerror
rejectsUnbalancedJournal        3  failed   failure
settlesBatchWithinSla           1  failed   flakyfailure
settlesBatchWithinSla           2  failed   flakyfailure
settlesBatchWithinSla           3  passed

  3 tests  2 passed  1 failed  1 flaky  66.7% pass

Three tests from seven attempts. Collapsing settlesBatchWithinSla into a single “passed” is how a flaky suite stays invisible for a year, and splitting it into three tests is how a pass rate stops meaning anything.

If your format has a status word for flakiness rather than attempt records, emit what you can and warn. normalize_status maps Playwright's flaky to xfailed so that it does not become unknown, but that is a fallback and not the intent: an adapter that can see the individual attempts should emit the individual attempts. Both definitions of flaky, within a run and across runs, are on the metrics page.

Map the status word, and keep the original

Run the framework's word through normalize_status and put the raw word in original_status:

from test_hub.domain.status import TestStatus, normalize_status

status = normalize_status(word)
if status is TestStatus.UNKNOWN and word:
    context.warnings.add("unknown_status", f"{word!r} has no canonical equivalent", location=path)

The table is a lookup, not a heuristic, and it is deliberately generous: it already knows ok, green, broken, crashed, inconclusive, unexpectedSuccess, notRunnable, expectedFailure and about sixty more, with case, whitespace, hyphens and underscores collapsed before lookup. A word it does not know becomes unknown — never passed by accident — and your warning is what tells the user their dialect needs one more line in the table. The round trip verified in the worked example below is "broken" → status: "error", original_status: "broken".

Safety: reports are untrusted uploads

Two of these are not negotiable.

Parse XML with defusedxml, never xml.etree

from defusedxml.ElementTree import iterparse as defused_iterparse

The two classic attacks are both entity tricks: a billion-laughs bomb that turns 200 bytes into gigabytes of resident memory, and an XXE that makes the server read /etc/passwd and put it into a stack trace on somebody's dashboard. Both are refused at the parser rather than mitigated afterwards. tests/fixtures/junit/billion-laughs.xml and xxe.xml exist to keep that true; both currently produce this, with no expansion at all:

{"error":"adapter_error","message":"this XML declares a DTD or entities and was
 refused before it was expanded. Entity expansion is how an 'XML bomb' turns a
 200-byte upload into gigabytes of memory, and how an XXE reads files off the
 server, so Test Hub never processes it. Re-export the report without a
 DOCTYPE.","detail":{"reason":"DTDForbidden"}}
HTTP 422

Add equivalent fixtures for your own format.

Stream; do not build a DOM

Use iterparse with elem.clear(), and detach each finished element from its parent as soon as you have turned it into events. The built-in JUnit adapter holds one suite's worth of elements plus the event it is currently yielding, whatever the file's size. A 200 MB Surefire aggregate parsed into a DOM is a multi-gigabyte resident set and an out-of-memory kill, which to whoever is watching looks like Test Hub crashing rather than like a large upload.

Two more, less dramatic and no less real

  • Do not build a path from anything in the file. The artifact store refuses names containing separators, .., NUL bytes or Windows device names outright rather than repairing them. If you emit artifact.published events, reduce a reported filename to its last component first.
  • Do not trust the file's own totals. tests="200" failures="3" is advisory and frequently wrong — a partially uploaded shard, a framework that counts retries, a hand-edited file. Counts are folded from the cases actually parsed. Emit a counts_mismatch warning when the file disagrees with you, rather than hiding the disagreement or, worse, believing it.

Registration is one entry point

[project.entry-points."test_hub.adapters"]
hopper = "test_hub_hopper.adapter:HopperAdapter"

The value may name a class, a zero-argument factory or a ready-made singleton; all three appear in the wild and all three work. The entry-point key is used only for logging — the registry keys on your adapter's .name attribute — so make the two match to save the next person some confusion.

Your package must be installedDiscovery is importlib.metadata.entry_points(group="test_hub.adapters"). A checkout on PYTHONPATH publishes no entry points and your adapter will not appear; pip install . or pip install -e . is what makes it exist. Test Hub's own two adapters carry a by-module-path fallback for exactly that situation, which is why junit-xml keeps working from a bare source tree and yours will not.

An entry point that raises on import is skipped with a warning rather than taking the process down. One broken plugin must not stop the server parsing a JUnit file, and it must not be silent either:

$ test-hub formats

skipping adapter entry point 'broken' (th_broken.adapter:BrokenAdapter): RuntimeError: this plugin was built against an older Test Hub

  3 adapter(s) installed
  …

Registering a name that already exists replaces the earlier adapter and logs a warning. That is deliberate: it is how an operator overrides a built-in with a patched fork without uninstalling anything.

src/test_hub_hopper/adapter.py

"""Adapter for the Hopper runner's JSON report."""

from __future__ import annotations

import json
import re
import uuid
from collections.abc import Iterator
from datetime import UTC, datetime
from typing import IO, Any

from test_hub.adapters.base import SNIFF_BYTES, BaseAdapter, ParseContext
from test_hub.domain.events import (
    DomainEvent,
    EventType,
    RunFinishedData,
    RunQueuedData,
    RunStartedData,
    SuiteFinishedData,
    SuiteStartedData,
    TestFinishedData,
    make_event,
)
from test_hub.domain.identity import TEST_HUB_NAMESPACE, suite_id, test_identity
from test_hub.domain.models import FailureDetail, utcnow
from test_hub.domain.status import normalize_status
from test_hub.errors import AdapterError

_MARKER = re.compile(rb'"hopper"\s*:')


def _event_id(source: str, run_id: uuid.UUID, sequence: int, kind: EventType) -> uuid.UUID:
    """Deterministic event id, so re-importing the same file applies nothing new."""
    return uuid.uuid5(TEST_HUB_NAMESPACE, f"{source}\x1f{run_id}\x1f{sequence}\x1f{kind}")


class HopperAdapter(BaseAdapter):
    name = "hopper"
    display_name = "Hopper JSON"
    extensions = (".hopper.json", ".hopper")
    content_types = ("application/vnd.hopper+json",)
    priority = 10
    description = "Hopper runner JSON reports (top-level \"hopper\" key)."

    def detect(self, stream: IO[bytes], filename: str | None, content_type: str | None) -> float:
        head = self.sniff(stream, SNIFF_BYTES)
        stripped = head.lstrip(b"\xef\xbb\xbf").lstrip()
        if not stripped.startswith(b"{"):
            return 0.0
        if _MARKER.search(head):
            return 0.9
        return self.hint_score(filename, content_type)

    def parse(self, stream: IO[bytes], context: ParseContext) -> Iterator[DomainEvent]:
        raw = stream.read()
        try:
            document: Any = json.loads(raw.decode("utf-8"))
        except (UnicodeDecodeError, ValueError) as exc:
            raise AdapterError(f"not valid Hopper JSON: {exc}") from exc
        if not isinstance(document, dict) or "hopper" not in document:
            raise AdapterError('this JSON has no top-level "hopper" key')

        header = document.get("hopper") or {}
        if header.get("version") != 1:
            context.warnings.add(
                "unknown_report_version",
                f"hopper report version {header.get('version')!r} is not 1; "
                "parsing it as version 1",
            )

        run_id = context.run_id
        source = context.source
        started = _timestamp(document.get("started_at")) or utcnow()

        def emit(kind: EventType, data: Any, when: datetime | None = None) -> DomainEvent:
            sequence = context.next_sequence()
            return make_event(
                kind,
                run_id=run_id,
                workspace_id=context.workspace_id,
                sequence=sequence,
                data=data,
                source=source,
                event_id=_event_id(source, run_id, sequence, kind),
                time=when or started,
            )

        yield emit(
            EventType.RUN_QUEUED,
            RunQueuedData(
                project_key=context.project_key,
                name=context.name or header.get("suite"),
                team=context.team,
                component=context.component,
                test_type=context.test_type,
                trigger=context.trigger,
                context=context.context,
                tags=list(context.tags),
                metadata=dict(context.metadata),
            ),
        )
        yield emit(EventType.RUN_STARTED, RunStartedData(started_at=started))

        seen: dict[str, uuid.UUID] = {}
        for case in document.get("cases") or []:
            path = str(case.get("group") or "hopper")
            if path not in seen:
                seen[path] = suite_id(project=context.project_key, suite_path=path)
                yield emit(
                    EventType.SUITE_STARTED,
                    SuiteStartedData(suite_id=seen[path], name=path.rsplit("/", 1)[-1], path=path),
                )

            status, original = _status(case.get("outcome"), path, context)
            failure = None
            if case.get("error"):
                failure = FailureDetail(
                    type=str(case["error"].get("kind") or "Error"),
                    message=str(case["error"].get("message") or ""),
                    stack_trace=case["error"].get("trace"),
                )
            yield emit(
                EventType.TEST_FINISHED,
                TestFinishedData(
                    test_id=test_identity(
                        project=context.project_key,
                        suite_path=path,
                        test_name=str(case.get("name") or "(unnamed)"),
                        params=case.get("params"),
                    ),
                    suite_id=seen[path],
                    name=str(case.get("name") or "(unnamed)"),
                    suite_path=path,
                    params=_params(case.get("params")),
                    attempt_number=int(case.get("attempt") or 1),
                    status=status,
                    original_status=original,
                    duration_ms=_millis(case.get("seconds")),
                    failure=failure,
                    stdout=case.get("stdout"),
                ),
            )

        for path, identity in seen.items():
            yield emit(EventType.SUITE_FINISHED, SuiteFinishedData(suite_id=identity))

        yield emit(
            EventType.RUN_FINISHED,
            RunFinishedData(finished_at=_timestamp(document.get("finished_at")) or utcnow()),
        )


def _status(word: Any, where: str, context: ParseContext):
    status = normalize_status(str(word or ""))
    if str(status) == "unknown" and word:
        context.warnings.add(
            "unknown_status",
            f"hopper outcome {word!r} has no canonical equivalent; recorded as unknown",
            location=where,
        )
    return status, (str(word) if word else None)


def _params(value: Any) -> str | None:
    if value in (None, "", {}, []):
        return None
    if isinstance(value, str):
        return value
    return json.dumps(value, sort_keys=True, separators=(",", "="))


def _millis(seconds: Any) -> int | None:
    try:
        return max(0, round(float(seconds) * 1000))
    except (TypeError, ValueError):
        return None


def _timestamp(value: Any) -> datetime | None:
    if not value:
        return None
    try:
        parsed = datetime.fromisoformat(str(value).replace("Z", "+00:00"))
    except ValueError:
        return None
    return parsed if parsed.tzinfo else parsed.replace(tzinfo=UTC)

Three details in there are the ones that matter.

  • Event ids are derived, not random. make_event defaults id to a fresh UUIDv4, which would make re-importing the same file apply everything twice. _event_id hashes (source, run_id, sequence, type) instead, so a repeated import of the same file into the same run is a no-op by construction. Both built-in adapters do exactly this. The flip side is real and worth stating: two different files imported into one run_id collide on those ids and lose events. One file, one run.
  • Every suite is announced before any result arrives. suite.started is emitted the first time a group is seen and all suite.finished events come at the end, because a dashboard that subscribes mid-import needs the tree before the leaves.
  • The run's own outcome is not emitted. RunFinishedData carries no status here; the server folds it from the attempts. Sending one would be ignored anyway for everything except cancelled.

The rules, in one place

Never claim what you cannot identify

No adapter may answer above 0.0 for arbitrary JSON or arbitrary XML. Require a discriminator your format really has. A 415 is a better outcome than a wrong number.

defusedxml only

Never xml.etree. DTDs and external entities are refused before expansion, not sanitized afterwards.

Stream, do not build a DOM

iterparse plus clear(). Memory should be a function of one suite, not of the upload size.

Warn rather than approximate

Anything you cannot represent exactly is a ParserWarning with a stable code. Never an exception, and never a quiet guess.

A retry is a new attempt

Increment attempt_number; never overwrite an outcome. The disagreement between attempts is the flakiness signal.

Derive identity

Always through test_hub.domain.identity, never from timestamps, line numbers, shards or run ids.

Formats we would like

The first release ships exactly two adapters, junit-xml and testhub-json, and says so plainly rather than advertising a matrix of formats it does not have. JUnit XML covers a lot of the world by accident — pytest, Surefire, Gradle, Jest, Playwright, Mocha and most of the rest can all emit it — which is precisely why it was the one to build first.

Everything below deserves a real adapter rather than a lossy JUnit export, and every one of them is a package somebody else can own and release on their own schedule.

FormatWhy it deserves its own adapter rather than a JUnit export
TRX (MSTest, dotnet test)Carries Outcome words JUnit has no room for — NotRunnable, Inconclusive, Timeout — all of which normalize_status already maps. It also has real per-test start and end times, which JUnit does not.
NUnit 3Native <test-case> with attachments, properties, and its own <reason>/<failure> split.
Cucumber / Gherkin JSONStep-level results. Flattening a scenario to one test throws away exactly the information a BDD suite exists to produce.
Jest (--json)Native output has per-assertion failure messages, ancestorTitles for the suite tree, and numRetries, none of which survive its JUnit reporter.
Playwright (--reporter=json)Attempts, traces, screenshots, videos and projects (browser × config) as first-class fields. This is the one where the JUnit export loses the most.
Maven Surefire (native)The rerunFailure/flakyFailure handling is already in junit-xml, but Surefire's own report XML additionally carries the full system-out per test and the rerun ordering.
Gradle test XMLSame family, different quirks around nested suites and standard-out placement.
Go (go test -json)A stream, not a document: an adapter could publish live over POST /runs/{id}/events as the events arrive. Subtests give a real hierarchy.
Rust (cargo test JSON, cargo-nextest)Nextest has retries and per-test timing; the libtest JSON stream has neither in a JUnit export.
Performance formats (JMeter JTL, k6 JSON, Gatling)These do not fit the pass/fail model cleanly, and pretending they do is worse than modelling them properly. TestType.PERFORMANCE exists; the interesting design question is what a “test” is when the answer is a latency distribution.

If you write one, the checklist is the six cards above. Everything else is your format's problem, which is the point of putting the seam where it is.
