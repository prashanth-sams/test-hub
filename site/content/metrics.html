Every number Test Hub shows is defined here and implemented once — in src/test_hub/domain/metrics.py and the computed fields of RunCounts in src/test_hub/domain/models.py. Nothing else in the Python codebase computes a pass rate, a flake rate or a percentile. A view that needs one calls in there, so the number in one part of the product and the number in another cannot disagree.

The executable version of this pagetests/test_metrics.py is this document as assertions. Almost every worked example below is lifted from it, and both change together when a definition changes. If you are about to argue with a number, that file is the fastest way to check whether you are right.

One implementation, and the one deliberate exception

There is exactly one second implementation of any of this, and it is on purpose: src/test_hub/web/assets/js/10-provider.js transcribes RunCounts's computed fields as finalizeCounts(), and percentile() line for line, into JavaScript. It has to, because some filters cannot be expressed to the API: the dashboard fetches the matching runs and recomputes a pass rate for "the payments team, staging only" in the browser.

The JavaScript carries the Python function names in its comments so the two stay greppable from each other. That is a real duplication and worth knowing about before you change a formula.

One place they genuinely differ Python's round() breaks ties to even; the JavaScript Math.round(value * 100) / 100 breaks them upward. One test passing out of 32 executed is 3.12 from the server and 3.13 from the browser's filtered recomputation. Both are verified; the divergence is at most 0.01 and only at an exact half-cent tie, but it is there.

The counting rule

One test contributes exactly one outcome to a run's counts, through its effective attempt. The effective attempt is the last one — not the best, not the worst:

def effective_status(attempt_statuses):
    if not attempt_statuses:
        return TestStatus.UNKNOWN
    return attempt_statuses[-1]

A test that failed and then passed on retry is green and flaky, and it counts as one pass. A test that passed and then failed on a rerun is red. The retry history is never discarded, so both facts stay on the page — that is the whole reason attempts are rows rather than overwrites.

Counts are always folded from the stored attempt rows, never taken from a publisher's own totals. A publisher's totals drift the moment anything is retried or a shard fails to upload, and a front page that disagrees with the run page it links to is worse than a slow one. The same rule is why a JUnit file's tests="5" failures="1" attributes are advisory: a mismatch produces a counts_mismatch warning, not a wrong number.

The count fields

RunCounts has thirteen stored fields and four computed ones. It is the same object for a run, a suite or any filtered slice.

FieldMeaning
totalTests folded into this block. Equals the sum of the ten status fields.
passed failed error skipped xfailed xpassed cancelled unknown running queued One per TestStatus, counting effective attempts.
flakyTests that were flaky within this run. Not a status: a test is counted here as well as under its effective status.
retriedTests with more than one attempt. Likewise not a status.

flaky and retried overlap with the status counts on purpose. They answer a different question — "how much of this run's green was earned on the second try" — and adding them into total would double-count the same tests.

completed and executed

completed = passed + failed + error + skipped + xfailed + xpassed + cancelled + unknown
executed  = completed - skipped - cancelled

completed is total minus the tests still in flight, so it is the honest denominator while a run is still streaming: running and queued are excluded. executed goes one step further and removes the tests that never ran a body. A skipped test cannot pass and cannot fail; putting it in the denominator turns "we skipped the slow suite today" into a pass-rate drop that reads exactly like a regression.

>>> counts = RunCounts(total=5, passed=3, running=1, queued=1)
>>> counts.completed
3
>>> counts.executed
3
>>> counts.pass_rate
100.0

That 100% is correct and it is also the thing to understand about a live run: it means "everything that has finished so far has passed", not "this run will pass". The dashboard shows the in-flight counts beside it for exactly that reason.

Pass rate and failure rate

pass_rate    = 100 * (passed + xfailed)          / executed
failure_rate = 100 * (failed + error + xpassed)  / executed

Both are rounded to two decimal places, and both are None when executed <= 0.

Why xfailed is a success and xpassed is not

A test marked expected-to-fail that failed did exactly what it was declared to do. Colouring it red trains people to ignore red, which is the most expensive failure mode a test dashboard has. So xfailed counts toward the pass rate.

xpassed counts as a failure instead, because an expectation that no longer holds is a signal: either the bug is fixed and the marker should go, or something else changed and nobody noticed. It is the one status where "the test passed" and "this is fine" come apart, and the code says so out loud in test_hub.domain.status.is_successful and is_failureish.

>>> counts = RunCounts(total=4, passed=1, xfailed=1, xpassed=1, failed=1)
>>> counts.pass_rate, counts.failure_rate
(50.0, 50.0)

Why pass_rate is null, not zero, when nothing executed

A run that only skipped has no pass rate. Rendering it as a red 0% is a lie the dashboard would then have to explain every time somebody asked; rendering it as "—" is the truth.

>>> counts = RunCounts(total=3, skipped=3)
>>> counts.executed
0
>>> counts.pass_rate is None, counts.failure_rate is None
(True, True)

Consumers have to handle the null. The JavaScript provider carries a comment saying so, for the same reason: a missing pass_rate must not become 0% on the way through the UI.

The two rates need not add up to 100

unknown sits in executed but in neither numerator. That is deliberate. An unmapped status word is not evidence of a pass and not evidence of a failure, and quietly assigning it to either would change the number the dashboard shows on the basis of a word Test Hub failed to recognize. Every unknown also raises an unknown_status parser warning attached to the run, so the gap is visible rather than mysterious.

This is real, not theoretical. tests/fixtures/canonical/report.json contains a test whose status is the word bananas:

$ test-hub ingest tests/fixtures/canonical/report.json --project checkout-service --json
  "counts": {"total": 6, "passed": 3, "failed": 1, "skipped": 1, "unknown": 1,
             "flaky": 2, "retried": 2, "completed": 6, "executed": 5,
             "pass_rate": 60.0, "failure_rate": 20.0}
  "warnings": [
    {"code": "unknown_status",
     "message": "status 'bananas' is not a word Test Hub knows; recorded as unknown",
     "severity": "warning", "location": "tests[6]"}
  ]

Six tests, one skipped, so executed is 5. Three passes over five is 60%; one failure over five is 20%; the missing 20% is the test nobody could classify.

RunCounts(total=12, passed=7, failed=2, error=1, skipped=1, xfailed=1):

>>> counts = RunCounts(total=10, passed=8, failed=1, skipped=1)
>>> counts.executed, counts.pass_rate
(9, 88.89)

Rates over many runs are test-weighted

The overview and the trend chart merge count blocks with RunCounts.merge and then compute the rate. That makes the result test-weighted rather than a mean of per-run rates: a 2000-test nightly and a 3-test smoke run do not carry equal weight in the portfolio number.

Both statistics are defensible and they answer different questions. Test-weighted asks "what fraction of our tests are green"; the unweighted mean of run pass rates asks "what fraction of our pipelines are healthy", and gives a tiny smoke suite the same vote as the nightly. Test Hub computes the first and does not compute the second — if you want it, the per-run rates are all in the API response.

Durations

A run

def run_duration_ms(started_at, finished_at, attempt_durations_ms=None):
    if started_at is not None and finished_at is not None:
        return max(0, round((finished_at - started_at).total_seconds() * 1000))
    if attempt_durations_ms is not None:
        total = sum(attempt_durations_ms)
        return int(total) if total else None
    return None

Wall clock wins whenever both ends are known, because with parallel workers the sum of test durations is not a duration anyone means. Eight xdist workers make it roughly eight times the number on the wall, and a chart of it tells you about your fleet's total CPU time, not about how long anybody waited.

>>> start = utcnow(); end = start + timedelta(seconds=30)
>>> run_duration_ms(start, end, [20_000, 25_000, 18_000])
30000

It runs the other way too, and that is the more common case in practice: a run whose two attempts reported 4100 ms and 3900 ms, published over HTTP by a script, stored duration_ms: 37. Thirty-seven milliseconds of wall clock, because the "run" was three curl calls and no test actually executed — the attempt durations came from the report, the wall clock came from the reporting. Neither number is wrong; they measure different things, and Test Hub stores the one that answers "how long was this run open".

The fallback, and its floor:

>>> run_duration_ms(None, None, [100, 200])
300
>>> run_duration_ms(None, None, []) is None
True
>>> run_duration_ms(None, None, None) is None
True

An empty list yields None rather than 0: zero milliseconds is a claim about how long something took, and "we do not know" is not that claim. The max(0, …) in the wall-clock branch is a floor for clock skew — a finished_at before started_at gives 0, not a negative duration.

A test, across its attempts

TestCase.duration_ms is the sum over every attempt:

return sum(attempt.duration_ms or 0 for attempt in self.attempts)

Retries are time the run actually spent. A test that took 30 seconds to time out and then 6 seconds to pass cost the run 36 seconds, and reporting only the successful 6 hides the most expensive tests in the suite behind their own flakiness. If you want the effective attempt's duration on its own it is attempts[-1].duration_ms, and it is in the payload.

Note that this is the opposite choice from the run, and for a consistent reason: a single test's attempts are strictly sequential, so summing them is wall clock. A run's tests are not.

TestAttempt fills in whichever of started_at, finished_at and duration_ms is missing when the other two are present, and the fold does the same on the way in, so an adapter that can only supply two of the three does not lose the third.

Flakiness

Test Hub has two flakiness definitions, at two altitudes. They answer different questions and neither is a substitute for the other.

Within a run

def is_flaky_within_run(attempt_statuses):
    if len(attempt_statuses) < 2:
        return False
    saw_success = any(is_successful(s) for s in attempt_statuses)
    saw_failure = any(is_failureish(s) for s in attempt_statuses)
    return saw_success and saw_failure

The test both succeeded and failed inside one execution of the suite. This is the strict definition: it needs two attempts, because a single attempt cannot disagree with itself, and it needs genuine disagreement rather than merely a retry.

>>> is_flaky_within_run([S.FAILED, S.PASSED])
True
>>> is_flaky_within_run([S.PASSED, S.FAILED, S.PASSED])
True
>>> is_flaky_within_run([S.FAILED, S.FAILED])
False
>>> is_flaky_within_run([S.PASSED])
False
>>> is_flaky_within_run([S.SKIPPED, S.PASSED])       # a skip is neither side
False
>>> is_flaky_within_run([S.PASSED, S.XPASSED])       # xpassed is failure-ish
True

That last pair is the definition earning its keep: xpassed counts as a failure for the rates, so it counts as the failure side here too, and a test that passed then unexpectedly-passed is flagged. Consistency across the two definitions matters more than any individual reading of that case.

This is what TestCase.flaky and RunCounts.flaky mean, and it is what the JUnit adapter's handling of Surefire's <flakyFailure> and <rerunFailure> elements exists to make visible.

Across runs — flake_rate

TestDetail.flake_rate is the percentage of runs in a trailing window in which a test misbehaved. The window is Settings.flaky_window_runs (default 20) for the overview's flakiest-tests list, 30 by default on GET /api/v1/tests/{id}?history=… (1–200).

def flake_rate(per_run):
    considered = [
        (status, within) for status, within in per_run
        if status not in (SKIPPED, CANCELLED, UNKNOWN)
    ]
    if len(considered) < 2:
        return None

    successes = sum(1 for s, _ in considered if is_successful(s))
    failures  = sum(1 for s, _ in considered if is_failureish(s))
    majority_is_success = successes >= failures

    disagreements = 0
    for status, within_run in considered:
        agreed = is_successful(status) if majority_is_success else is_failureish(status)
        if within_run or not agreed:
            disagreements += 1
    return round(100.0 * disagreements / len(considered), 2)

Four rules, each worth stating on its own.

  1. Runs where the test did not execute are dropped

    Not counted as agreement — dropped. skipped, cancelled and unknown enter neither the numerator nor the denominator, so a test that was skipped for a month does not accumulate a month of apparent stability.

  2. Two executed runs are the minimum

    One data point cannot describe consistency. Returning 0.0 for it would put every brand-new test at the bottom of the flakiest list — the right place, for entirely the wrong reason, and it would stay there until it broke. None is the honest answer and the dashboard renders it as "—".

  3. The majority is the baseline, ties going to success

    A run disagrees when its effective outcome is not the window's majority outcome. The tie rule (successes >= failures) means a test that is up half the time and down half the time scores 50%, from either direction.

  4. A run that was flaky within itself always counts as a disagreement

    Even when its final outcome agreed with the majority. A test that reached green only because it was retried is not the same as a test that was green, and a majority-only rule would score it 0% and hide it.

per_run is ordered oldest first. The repository reverses its newest-first history before calling in, and says so in a comment, because every list it returns is newest-first and exactly one of them has to flip.

History (oldest first)ConsideredMajorityDisagreementsflake_rate
pass, pass, pass, fail4success125.0
pass, pass, fail, fail4success (tie)250.0
pass, fail, fail, fail4failure125.0
pass, pass (second one retried)2success150.0
error, pass2success (tie)150.0

Every row was run against the shipped function. The fourth is the one that motivates rule 4: both runs ended green, so a majority-only rule would report 0% and the test would stay invisible despite needing a retry half the time. The last row is rule 1 and rule 2 together — the skip is dropped, which leaves one considered run, which is not enough.

metrics.py also exports a boolean is_flaky_across_runs(statuses), true when a sequence of effective outcomes contains both a success and a failure. Nothing in the server uses it; flake_rate is what the repository calls, because a rate is more useful than a boolean when you are ranking twenty thousand tests. It is exported and tested for consumers that want the cheap answer over a window they chose themselves. aggregate_counts(statuses) is in the same position: exported, tested, and not on the write path, which uses RunCounts.add directly.

TestDetail.failure_rate is a different quantity

Not the same denominator as RunCounts.failure_rate, and not in metrics.py — it is computed in SqlRunRepository.get_test_detail:

executed = [s for s, _ in oldest_first if s not in (SKIPPED, CANCELLED, UNKNOWN)]
failure_pct = round(100.0 * sum(1 for s in executed if is_failureish(s)) / len(executed), 2)

It is "in what fraction of the runs where this test actually ran did it fail", over the same window flake_rate uses. RunCounts.failure_rate is "what fraction of the tests in this run failed". Both are labelled failure rate in the UI because in their own contexts both readings are the obvious one — but they are different quantities and comparing one against the other means nothing.

TestDetail.average_duration_ms is the arithmetic mean of the per-run TestCase.duration_ms values that were recorded, which — per the rule above — are already sums across attempts. A test that is retried often will look slower here than its typical successful attempt, and that is the intended reading.

Percentiles

The trend chart's duration_ms_p50 and duration_ms_p95 come from a percentile written out by hand:

def percentile(values, fraction):
    if not values:
        return None
    ordered = sorted(float(v) for v in values)
    if len(ordered) == 1:
        return ordered[0]
    position = max(0.0, min(1.0, fraction)) * (len(ordered) - 1)
    lower = int(position)
    upper = min(lower + 1, len(ordered) - 1)
    weight = position - lower
    return ordered[lower] * (1.0 - weight) + ordered[upper] * weight

Linear interpolation between the two nearest ranks, with fraction clamped into [0, 1]. It is written out rather than taken from statistics.quantiles so the trend numbers are identical on every supported Python, reproducible by hand from the raw durations the API returns, and transcribable into the JavaScript provider without a second opinion about which of the nine standard percentile definitions to use.

>>> percentile([10], 0.95)
10.0
>>> percentile([], 0.5) is None
True
>>> percentile([1, 2, 3, 4, 5], 0.5)
3.0
>>> percentile([1, 2, 3, 4], 0.0)
1.0
>>> percentile([1, 2, 3, 4], 1.0)
4.0
>>> percentile([1, 2, 3, 4], 0.5)      # the interpolation, visible
2.5

It can produce the usual binary-floating-point artefacts — percentile([100, 200, 300, 400, 500], 0.95) is 479.99999999999994 — but TrendPoint stores round(p95) as an integer, so what reaches the wire is 480.

A bucket with one runA single run in a trend bucket makes p50 and p95 the same number, because percentile short-circuits on a one-element list. That is correct, and it is also why the trend chart is not worth reading at a one-day bucket on a quiet project. Buckets widen automatically past 60 points, and a bucket with no runs at all is still emitted so the chart shows a genuine gap instead of a straight line implying continuity.

Where a run's status comes from

The run's own status is folded too, in SqlEventRepository._fold_status, and it does not use worst_status. The conditions are checked in this order:

ConditionResult
the run was explicitly cancelledcancelled
finished_at is set and error > 0error
finished_at is set and (failed > 0 or xpassed > 0)failed
finished_at is set and total == 0unknown
finished_at is setpassed
any attempt exists, or started_at is setrunning
otherwisequeued

cancelled is the one outcome a publisher can dictate, because a cancelled run is indistinguishable from a run that stopped reporting; everything else is derived from the attempts. A finished run with no tests at all is unknown, not passed — an empty suite has no outcome. All seven rows are verifiable against a live server, and the event contract shows what happens when a publisher claims otherwise.

worst_status in domain/status.py is a different function for a different job: it folds a set of attempt statuses into the most severe one, and is used by the JUnit adapter to give a single verdict to a <testcase> carrying several outcome elements. It orders unknown < skipped < xfailed < passed < xpassed < queued < running < cancelled < failed < error, and an empty iterable is unknown.
