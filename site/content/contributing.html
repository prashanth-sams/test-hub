Getting set up

$ git clone https://github.com/prashanth-sams/test-hub
$ cd test-hub
$ python3 -m venv .venv && source .venv/bin/activate
$ pip install -e ".[dev]"

Or with uv, which is noticeably faster and equally supported for development:

$ uv venv && source .venv/bin/activate
$ uv pip install -e ".[dev]"

Python 3.11 or newer. Nothing else — no database server, no Node, no container runtime. Check it works:

$ test-hub demo && test-hub serve

The shape of the codebase

PackageHolds
domain/The contract: canonical models, the event envelope, status normalization, test identity, every metric formula. No I/O.
adapters/Report formats. Bytes in, domain events out. No database.
storage/Repository protocols and the SQLite implementation, plus Alembic migrations.
service/Orchestration: imports, live runs, the event bus, the application context.
api/FastAPI app, routes, security, public request and response models.
cli/Typer commands. Thin wrappers with no business logic.
export/The standalone HTML snapshot writer.
sdk/The Python publishing client.
web/The dashboard, shipped inside the wheel.

The layering rule

cli ──▶ api ──▶ service ──▶ storage ──▶ (sqlite / filesystem)
 │       │         │
 │       │         └──▶ domain ◀── adapters
 ├──▶ export ──────────▶ domain
 └──▶ sdk ─(http)─▶ api

domain imports nothing else from the package. That is what lets an adapter, a publisher or a test depend on the contract without pulling in FastAPI, SQLAlchemy or a database — and it means a cycle shows up immediately as an ImportError rather than as a slow build. storage never imports api. adapters import only domain.

If a piece of logic wants to reach across those lines, it belongs in service. This is the most common reason a change gets sent back.

The gates

All four run in CI on Linux, macOS and Windows across Python 3.11, 3.12 and 3.13. Run them before you push:

$ ruff check .            # lint
$ ruff format --check .   # formatting, including Python inside Markdown
$ mypy                    # strict, on src/
$ pytest                  # the suite

mypy runs in strict mode over the whole package and currently reports nothing. A new type: ignore needs a comment explaining what it is working around.

There is a fifth gate that catches the failures which embarrass a release: CI builds the wheel, installs it into a clean virtualenv in a directory with no checkout, and runs test-hub demo and test-hub export from there. A data file left out of the wheel, an entry point that does not resolve, or an exporter emitting a file that references assets only present in the source tree — all of those pass every other check and fail that one.

Writing tests

Fixtures live in tests/fixtures/ and are invented — plausible-looking reports for imaginary projects. Nothing is copied from a real-world report, and new fixtures should keep it that way.

A few conventions worth knowing:

  • The context fixture gives a fully wired application on a temporary database; client gives a TestClient bound to it.
  • live_server boots a real Uvicorn on a free port. Use it for anything involving Server-Sent Events — TestClient runs the app on the calling thread's portal and cannot interleave a streaming response with concurrent requests, so every interesting SSE property is untestable through it.
  • Import test_identity under an alias. pytest collects any module-level name beginning with test_, including imports, and will try to run the function under test as a test case.
  • Mark anything that starts a server or builds a large input @pytest.mark.slow.

The browser checks

Rendering, contrast in both themes, keyboard order, the 375 px layout, and that a test named <script>alert(1)</script> displays as text are checked with a real browser. Those checks are deliberately not in the pytest suite: they would put a 180 MB browser download in front of every contributor for a part of the codebase most changes do not touch.

The static half — no innerHTML with data, no CDN, no inline scripts, both theme token blocks present, both providers on one interface — is in the suite, in tests/test_frontend_assets.py, and runs everywhere.

To run the browser checks yourself:

$ npm install playwright && npx playwright install chromium
$ test-hub demo && test-hub serve --port 8971 &
# then drive http://127.0.0.1:8971 with Playwright
If you change the dashboard Re-run those checks and say in the pull request that you did. The static tests will catch a broken invariant; only a browser will catch a broken layout.

Adding a report format

The most valuable contribution available, and it does not require touching Test Hub at all — adapters are entry-point plugins, and the two built-in ones register through exactly the mechanism a third-party package uses. The adapter guide has a complete worked example, including the rules: never claim arbitrary JSON or XML, parse untrusted XML with defusedxml only, stream rather than build a DOM, raise a warning rather than approximate, and record a retry as a new attempt.

Formats we would particularly like: TRX, NUnit, Cucumber JSON and messages, Jest JSON, Playwright JSON, Maven Surefire's native form, Gradle, Go test, Rust test, and the performance-testing formats.

Changing the documentation

Long-form reference lives in docs/*.md. The website is built from site/content/*.html by site/tools/build.py, which uses only the standard library:

$ cd site
$ python3 tools/build.py          # rebuild
$ python3 tools/build.py --check  # what CI runs — fails if the output is stale

The built pages are committed, so a content change without a rebuild is a red check. site/README.md has the page format and the component vocabulary.

Commits and pull requests

Conventional-commit prefixes — feat:, fix:, docs:, refactor:, test:, chore: — with a ! or a BREAKING CHANGE: footer for anything that changes the wire contract.

In the pull request, say what changed and why, and what you ran. If the change touches the canonical model or the event envelope, say whether SCHEMA_VERSION needs to move — it changes only on a breaking change, and a release that moves it says so in its own section of the changelog.

Releasing

  1. Update the version

    src/test_hub/version.py is the single source; Hatchling reads it at build time.

  2. Write the changelog entry

    For the person reading pip list --outdated and deciding whether to upgrade, not for the person who wrote the patch.

  3. Tag it

    git tag v0.1.0 && git push --tags.

  4. The workflow publishes it

    release.yml builds and publishes to PyPI with Trusted Publishing over OIDC. There is no API token anywhere in the repository or in the settings — configure the publisher on PyPI first.
