The shell

Every view shares a navigation rail — the brand, Overview, Analytics and Runs, with the dark-mode switch at its foot — and a top bar carrying a relative timestamp of the last refresh, a connection indicator and the settings menu. Below 860px the rail becomes a bar: a phone has no width to spare for a permanent column.

The connection indicator has three states — Connecting, Live and Reconnecting. In live mode it reflects the Server-Sent Events stream: green and "Live" means results are arriving as they happen. When the stream drops, a banner appears above the view and the dashboard keeps working from what it already has; it reconnects by itself, and if it has been away long enough for the server's replay buffer to have moved past it, it refetches instead of quietly displaying stale numbers. In an offline export there is nothing to connect to, so the indicator says so and the banner never appears.

Every view is addressable. The routes are hash-based — #/overview, #/analytics, #/runs, #/runs/<uuid>, #/tests/<uuid> — with filters carried in the query part, so "the failing integration runs on main for payments" is a link you can paste into an incident channel. Hash routing is not a stylistic choice: it is the only kind that survives being opened from file://, where there is no server to answer a real path.

ThemeThe dashboard follows your operating system until you touch the toggle, then remembers your choice. Dark is a designed counterpart rather than an inversion: surfaces darken, ink lightens, and the status language — pass green, fail red, error deep red, skip amber, xfail purple, running blue — survives the switch, so a screenshot taken in either theme reads identically to a colleague.

Overview — the portfolio

The executive altitude. It answers four questions and refuses to answer any others: how much testing happened, how much of it passed, is it getting better or worse, and what is on fire right now.

Window and filters

A segmented control picks the window — 7, 14, 30 or 90 days — and six filters narrow it: project, team, component, test type, environment and branch. The dropdown values are facets the server computes from the data that is actually there, so you are never offered a filter that matches nothing. The same filter vocabulary is used on the Runs view, which is what lets a selection carry from one to the other.

The KPI row

Six tiles: Tests, Passed, Failed, Error, Skipped and Running. Two things about them are deliberate and worth knowing.

They count tests, not runs — the run count is the sub-label under "Tests". And a pass rate with nothing executed renders as an em dash rather than 0%. A suite that only skipped is not a 0% suite, and showing it in red trains people to ignore red.

Outcomes, health, volume, trend and duration

  • Test outcomes — the run's status mix as a single proportional bar, in the status colours, with a legend. Statuses with a zero count are omitted rather than drawn as slivers.
  • Health — the headline pass rate for the window, with the counts spelled out underneath in a sentence.
  • Volume by day — tests executed per day. This is the chart that tells you a suite stopped running before it tells you the suite started failing.
  • Pass rate trend — pass rate and failure rate per day across the window.
  • Run duration — p50 and p95 per day. Both, because a mean hides the shard that takes eleven minutes.

Every chart is inline SVG, drawn by the dashboard itself, reading its palette back out of the CSS custom properties. That is why they re-colour correctly the instant you switch theme, and why there is no charting library in the wheel.

Active runs and project health

Active runs lists what is queued or running right now, and is the panel the demo data deliberately keeps one run open for. When nothing is running it says so rather than showing an empty table.

Project health is one row per project: runs in the last 24 hours, last run and its status, pass rate with a delta against the previous period, live runs, and a count of flaky tests. Below that, the worst offenders — the tests failing most often, and the flakiest — each linking straight to its test page.

An empty overview that is not an empty installIf every run in the workspace is older than the selected window, the overview says exactly that instead of rendering a blank state that looks like a fresh installation. The payload carries both total_runs (inside the window) and total_runs_all_time so the view can tell the two apart.

Analytics — what keeps going wrong

The overview says how the portfolio is doing. Analytics sits one level below it and answers the four questions that come immediately afterwards: what broke, where, whose it is, and what it costs.

It reads the five most recent finished runs that match the filters, in full, plus the same overview payload the dashboard uses. In full is the point — failure taxonomy, ownership and per-test timings need every attempt of every test, and no summary carries those. Runs still in flight are skipped: half a run's failures classified as if they were all of them is a wrong answer, not a partial one. Finished runs cannot change, so their payloads are cached and a live update costs one overview request.

The tiles

Six numbers, each with the sentence that stops it being misread. Stability score is the pass rate less the share of executed tests that flaked — a suite where everything passes on the second attempt is not a healthy suite, and a pass rate alone says it is. Pass rate, last run carries its delta against the previous comparable run. Flaky tests, failing in the last run, runs analysed and time in tests complete the row.

Why runs fail

Failures grouped by the exception that raised them, ordered by weight, each with the tests behind it. Forty failures that are all one AssertionError in one fixture is one bug; forty spread over six exception types is six — and that distinction is the whole reason the card exists. A test that failed the same way in four of the five runs carries a multiplier rather than appearing four times, and a type containing something that was passing in the previous run is marked new. Failures the framework did not classify are filed as Unclassified, never under the test's own name, which would give every failure its own bucket and turn the taxonomy into a list.

Suites, owners and time

Suite hotspots stacks failing results against everything else for the busiest suites. Who owns what is the same numbers per owner, with everything unclaimed counted honestly as unclaimed rather than hidden. Where the time goes sums each test's duration across those runs by its stable identity: a test that takes four seconds every run costs twenty seconds of the last five, and that — not its single worst appearance — is what decides whether it is worth fixing.

What history says

The one card on the page that is about the window rather than the recent runs. Each test gets one cell per recent run, oldest on the left, and one of four words: stable (passed every time it ran), flaky (both passed and failed), broken (has not passed) and quiet (too few runs to say). The order is deliberate: a test that has never passed is not a flaky test, it is an unfinished one.

Runs — the drill-down's front door

Every run, newest first, with the full filter set: a free-text search over run name, branch, commit and tags, plus project, team, component, test type, environment, branch and status. Sort and page are here too.

All of it lives in the URL. That is the feature, not tidiness: a filtered list has to be a link somebody can paste, and it has to survive a reload and the back button. Sorting is handled by the server in live mode and in the browser in an offline snapshot — the view knows about neither, it just puts sort and dir in the hash and lets whichever provider is mounted honour them.

Each row carries the run's status, project, team and component, its environment and branch, the framework and language if the publisher said, the counts, the duration, and a live badge while it is still going.

Run detail — everything about one run

The engineering altitude: what a person needs when a pipeline has just gone red.

Run context

Where the run came from — framework and version, language, environment, branch, commit, CI provider, pipeline id and a link to the pipeline, hostname, OS, and who started it. Every field is optional, because publishers know varying amounts, and the panel shows what it was told rather than inventing placeholders.

Compared with the previous run

The panel that earns its place. It shows deltas for pass rate, duration and test count, then five lists:

ListWhat it means
Newly failingPassed in the baseline, fails now. This is the list you read first.
Still failingWas already broken. Not your regression, but not nothing.
Newly passingWas broken, is fixed.
AddedTest identities that did not exist in the baseline run.
RemovedIdentities the baseline had and this run did not report — deleted, renamed, or not collected.

The baseline is the previous comparable run: same project, team, component, test type, environment and branch. When there is no such run the panel says so, in those words, rather than comparing against something unlike it and producing a delta that means nothing. There is a link to open the baseline.

Why "Removed" is not always alarmingA renamed test is a removed identity and an added one, because identity is derived from the name. That is the correct answer — it genuinely is a different test now — but it means a refactor produces a long "Removed" list. Read it alongside "Added".

Parser warnings

If the import could not represent something exactly, it is on this panel: severity, code, message and where in the input it happened. An unmapped status word, a timestamp with no UTC offset, a truncated stack trace, counts that disagreed with the file's own header. Nothing is swallowed, because a warning you cannot see is a number you cannot trust.

Suites and tests

The suite tree, with each suite's counts and duration, expandable to the tests inside it. Below that, every test in the run as a searchable, sortable table: status (with a flaky pill where it applies), name, parameters, attempt count and duration.

The table's own search, status filter and sort are view-local rather than in the URL: they are a way of reading one page, not a place anybody links to. The run itself, and every test on it, are linkable.

Artifacts

Files attached to the run — screenshots, videos, logs, traces, coverage, and the raw uploaded report if store_raw_reports is on. They are stored content-addressed, so the same screenshot uploaded from fifty parallel shards is one stored object. They are always served as an attachment with the stored content type and X-Content-Type-Options: nosniff, never inline: an artifact is attacker-supplied content sitting on the dashboard's own origin.

Test detail — one test, across every run

This page exists because identity is stable. A test that got a new id every run would have no history, could not be called flaky, and could not be compared with itself.

The numbers

Flake rate, failure rate, average duration with a small duration trend, and the attempt count in the latest run. Flake rate is the percentage of runs in the trailing window in which this test behaved flakily — it was flaky within that run, or its outcome disagreed with the window's majority. Fewer than two usable runs and it renders as nothing at all: one data point cannot describe consistency.

Latest result, attempt by attempt

Every attempt gets its own panel, in order, each with its status, the framework's original word for that status where it differed, the duration, the failure type and message, the stack trace, and any stdout, stderr or captured logs.

A retry is a separate execution with its own output, not a correction of the one before it — so the failure that a rerun later "fixed" is still on the page. That is the argument for the event model, made visible.

The bytes are the bytesStack traces, logs and stdout arrive as text nodes inside a <pre>. There is no formatting pass, no ANSI translation and no markup: what the framework produced is what you read. A test named </script><img src=x onerror=alert(1)> renders as that text, in both the live dashboard and the offline file, and there is a test asserting it.

History

A strip of squares, newest on the left, one per run, each coloured by outcome and linking to its run — the shape of a flaky test is visible at a glance. Underneath, the same history as a table: run time, status, attempt count, duration, branch and environment.

In an offline exportA snapshot contains the runs it was built from, so a test's history in an exported file is bounded by what that export included. When it is partial the page says so on a banner rather than presenting a short history as a complete one.

The same dashboard, offline

Everything above is identical in the file test-hub export writes. The views, the charts, the filters, the routing, the theme toggle. What differs is where the data comes from: a frozen snapshot object embedded in the page instead of a REST API and an event stream. The footer of an exported file names the generator version and how many runs are in it.

What an export cannot do is update while you watch, and it cannot fetch a run that was not included in it. Those are the two things the live mode is for.
