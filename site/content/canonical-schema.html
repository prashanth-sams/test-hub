The models live in test_hub.domain.models and are the public wire contract. The SQLAlchemy rows on disk are a separate, private thing, and nothing ever serializes an ORM object. That separation is what lets the table layout change — a new index, a split table, PostgreSQL — without a version bump that every consumer has to react to.

schema_version and what it promises

One integer, defined once in test_hub/version.py. It moves independently of the package version and only on a breaking change.

$ test-hub --version
test-hub 0.1.0 (canonical schema v1)

$ curl -s http://127.0.0.1:8000/healthz
{"status":"ok","version":"0.1.0","schema_version":1,"database":"ok",
 "workspace_id":"b037a4b3-53f8-5326-a5d5-f5fad3c31052","live_subscribers":0,
 "time":"2026-09-09T03:30:44.034812Z"}

/healthz is the cheapest way for a consumer to find out what a server speaks before sending it anything.

Which payloads carry the version

Only the ones allowed to cross a version boundary on their own — a top-level document a consumer might have received with no surrounding context.

Carries schema_versionDoes not
TestRun, RunDetail, TestDetail, OverviewSnapshot, ImportResult, Snapshot, and DomainEvent (as schemaversion, following the CloudEvents attribute-naming rules) Workspace, Project, RunSummary, RunCounts, TestSuite, TestCase, TestAttempt, Artifact, RunComparison, TestHistoryPoint, TrendPoint, ProjectHealth, ParserWarning, FailureDetail, RunContext

A TestCase is only ever seen inside a RunDetail, so stamping a version onto it would put the same integer on every one of ten thousand objects in the same document.

The compatibility promise

Within a major schema version:

  • Fields may be added. A new optional field on any model is not a breaking change, so a consumer must tolerate one.
  • Fields are not removed, renamed or retyped.
  • The meaning of a field does not change. In particular the metric definitions are part of this contract rather than an implementation detail: changing what pass_rate counts is a version bump even though the field's name and type are untouched.
  • Enum members may be added. TestStatus, RunStatus, TestType, TriggerType and ArtifactKind are closed sets for this version, but the honest reading is that a future release could add one. Treat an unrecognized member the way you would treat unknown or other, not as a crash.

Anything else — a removed field, a changed formula, a new event type, a different envelope shape — is a SCHEMA_VERSION bump.

What happens when the version is not the one this build speaks

It is refused, not coerced. Every versioned model validates the integer:

>>> TestRun.model_validate({..., "schema_version": 2})
ValidationError: Value error, unsupported schema_version 2; this build speaks 1

End to end, importing a test-hub-report that declares version 2:

$ test-hub ingest report-v2.json --project storefront-web

  error: this build speaks Test Hub schema_version 1, but the document declares 2.
  Upgrade Test Hub (a newer document) or re-export the report with a publisher
  that targets version 1.
    document_schema_version: 2
    supported: 1
{"error":"validation_error",

HTTP 422

The reasoning is worth repeating because it is the reason for the whole design: an older Test Hub reading a newer document cannot know which fields changed meaning, and a wrong pass rate is worse than a failed import.

What a consumer should do

The same thing, in the same direction, with one asymmetry.

  • Version higher than you know: refuse, and say so. You cannot know what changed. Failing loudly gives the operator something to act on; guessing gives them a dashboard that is quietly wrong.
  • Version lower than you know: you may accept it if you are prepared to supply defaults for fields that did not exist yet. Test Hub itself does not do this, because there is only one version so far, but a consumer with a migration table can.
  • Version absent: assume the version you were built for. Every model defaults schema_version rather than requiring it, so a report hand-written without one is read as version 1 rather than rejected. That is a convenience for people writing JSON by hand, and it means a document with no version is not evidence of anything.

Unknown fields are rejected, not ignored

Every canonical model is extra="forbid":

>>> RunCounts.model_validate({"total": 1, "passed": 1, "typo_field": 3})
ValidationError: 1 validation error for RunCounts
typo_field
  Extra inputs are not permitted [type=extra_forbidden, input_value=3, input_type=int]

This is the opposite of the usual advice about being liberal in what you accept, and it is deliberate. A silently ignored durationMs produces a run with no durations and no error anywhere; a 422 naming the field produces a five-second fix. The one place the rule is relaxed is AdapterInfo in the API layer, which ignores extra keys so that a third-party adapter describing itself with unfamiliar fields cannot break GET /api/v1/adapters for everyone else.

This applies to the models, not to the report documentThe test-hub-report JSON below is read by an adapter that walks plain dictionaries, so a key it does not recognise inside a test entry is skipped without a warning. Model-level strictness begins after the adapter has built a payload. Spell the field names in the tables below exactly.

Round-tripping a response

Computed fields — pass_rate, executed, a test case's status — are written out but derived, so extra="forbid" would normally reject a client that read a response and validated it straight back into the same model. The shared base drops exactly the computed names, and nothing else, on the way in. The round trip works and a genuine typo is still an error:

>>> counts = RunCounts(total=2, passed=1, failed=1)
>>> RunCounts.model_validate(counts.model_dump(mode="json")).pass_rate
50.0

Three field aliases worth learning once

AliasDefinitionUsed for
Slug1–120 characters, ^[a-zA-Z0-9][a-zA-Z0-9._\- ]*$Project keys, teams, components, environments, tags
ShortText≤ 512 charactersNames, paths, class names, single-line free text
LongText≤ 64 000 charactersStack traces, stdout, stderr, logs

Slug is deliberately permissive about case and spaces, because real team names have both, and deliberately strict about everything else, because these values end up in filenames, URLs and SQL LIKE patterns. It is not a lowercase-hyphenated slug in the blog-URL sense.

Event payloads type these same fields as bare str, which means a value can pass event validation and still be unstorable. Two layers deal with that, in opposite directions and on purpose. Adapters drop a bad slug with an invalid_slug warning, because a file should not be able to invent a team name. The storage layer repairs one, replacing disallowed characters with -, because a run that has already been accepted should not be lost over a slash in a team name.

LongText has a second ceiling above it, TEST_HUB_MAX_TEXT_FIELD_BYTES (256 KiB by default). The smaller of the two wins, truncation sets FailureDetail.truncated or a text_truncated flag in the attempt's metadata, and redaction runs before truncation so that a cut can never leave the tail of a secret behind.

Every timestamp is an aware datetime in UTC. A naive datetime is a validation error everywhere, including on the way out of the database: the ORM stores a fixed-width ISO-8601 string precisely so that pysqlite cannot hand back a naive value.

Workspace

The tenancy boundary. The open-source edition creates exactly one, default, and gives it no UI — but every row in the database carries its id from the first migration, because adding a tenancy column to a populated events table later is the migration nobody wants to write.

Its id is derived rather than random: uuid5(TEST_HUB_NAMESPACE, "workspace\x1f" + slug.lower()). So default is the same UUID on every installation — b037a4b3-53f8-5326-a5d5-f5fad3c31052, the value in the /healthz output above. That is what lets an offline publisher compute workspace-scoped identities without asking a server. If an existing database disagrees, the database wins and a warning is logged. The other fields are slug, name and created_at.

Project

Created implicitly on first import. key is the stable, human-typed value a publisher sends (payments-api); id is internal. Also: workspace_id, name, description, default_team, repository_url, tags (at most 64 slugs), created_at and updated_at.

The ten statuses

Test Hub stores exactly one normalized status per attempt and always keeps the source report's own word beside it in TestAttempt.original_status. Normalization is therefore never lossy: you can always find out what the framework actually said.

passed failed error skipped xfailed xpassed running queued cancelled unknown

StatusMeaningCounts as
passedThe test ran and succeeded.Numerator of the pass rate.
failedAn assertion did not hold.Numerator of the failure rate.
errorThe test did not get as far as a verdict — an exception, a fixture blowing up, a crashed process.Numerator of the failure rate.
skippedDeliberately not run.Excluded from both denominators.
xfailedExpected to fail, and did.Numerator of the pass rate — the test behaved exactly as declared.
xpassedExpected to fail, and passed.Numerator of the failure rate — an expectation that no longer holds is a signal.
cancelledThe run was stopped before this test finished.Excluded from both denominators.
running queuedIn flight. Only seen on a live run.Excluded from completed, and therefore from everything downstream.
unknownThe source said something Test Hub does not recognise.Counted in completed and executed but in neither rate numerator, so it visibly drags the pass rate down rather than hiding.

The normalization is a lookup table, not a heuristic

normalize_status collapses case, whitespace, hyphens and underscores and then looks the word up. The table is deliberately generous — it already knows ok, green, broken, crashed, inconclusive, notRunnable, unexpectedSuccess, expectedFailure, timedOut, ambiguous and about sixty more, grouped in the source by the framework family that spells it that way.

>>> normalize_status("Success")
<TestStatus.PASSED: 'passed'>
>>> normalize_status("expected failure")
<TestStatus.XFAILED: 'xfailed'>
>>> normalize_status("weird")
<TestStatus.UNKNOWN: 'unknown'>

A word it does not know becomes unknown and the adapter raises an unknown_status warning. It never becomes passed by accident. That is the entire reason the mapping is a table: a heuristic that treats anything non-negative as a pass will eventually turn somebody's deferred into a green tick, and nobody will find out.

Playwright's “flaky”The word maps to xfailed so that a report carrying it verbatim in a status column does not become unknown. It is a fallback, not the model: flakiness in Test Hub is derived from disagreeing attempts, so an adapter that can see the individual attempts should emit them instead.

Stable test identity

A test's identity has to survive being re-run, re-ordered, re-parameterized in a different order, moved to a different line and executed on another machine by a different framework version. If it does not, every run invents a new set of tests, and history, comparison and flakiness are all worthless.

Three identities are therefore derived rather than assigned, as UUIDv5 in one fixed namespace:

TEST_HUB_NAMESPACE = uuid.UUID("4c8f4c4d-3ecb-5f78-a1e4-c1a24e07b1e6")
IdentityHashed input
workspace"workspace" \x1f slug.lower()
suite"suite" \x1f project \x1f suite_path
testproject \x1f suite_path \x1f class_name \x1f test_name \x1f params

The namespace is hard-coded and must never move: every historical identity would change with it. \x1f is the ASCII unit separator, chosen because it cannot appear in any of the fields. identity_source() is public and tested precisely so that an implementation in another language can reproduce the string byte for byte:

>>> identity_source(project="storefront-web", suite_path="specs/checkout/payment",
...                 class_name="CheckoutPayment", test_name="declines an expired card",
...                 params={"currency": "EUR"})
'storefront-web\x1fspecs/checkout/payment\x1fCheckoutPayment\x1fdeclines an expired card\x1fcurrency=EUR'

>>> test_identity(project="storefront-web", suite_path="specs/checkout/payment",
...               class_name="CheckoutPayment", test_name="declines an expired card",
...               params={"currency": "EUR"})
UUID('f44a4d33-b813-54db-a7c6-b16bf824cd48')

That UUID is the id the API returns for that test after the import below, computed offline with no server involved. It is what makes a publisher in another language possible at all.

Normalization before hashing

Each component is normalized to Unicode NFC, has its whitespace collapsed, and is stripped; suite paths are converted to forward slashes with a leading ./ removed. Parameter values are rendered with their volatile fragments scrubbed: <Foo object at 0x7f3c…> becomes object at 0x?, a bare UUID becomes <uuid>, and a long hex literal becomes 0x?. They are replaced with a stable token rather than dropped, so that two genuinely different parameters do not collide.

Named parameters are sorted by name; positional parameters keep their order, because position is the name.

>>> normalize_params({"b": 2, "a": 1})
'a=1|b=2'
>>> normalize_params(["chrome", 1024])
'0=chrome|1=1024'
>>> test_identity(project="p", suite_path="tests/t.py", test_name="x") == \
...     test_identity(project="p", suite_path="./tests/t.py", test_name=" x ")
True

The test-hub-report JSON format

Test Hub's own report format, for when your framework has no JUnit writer or when JUnit XML would lose something you care about. It is the reference publisher contract: everything the canonical model can hold is expressible here, which is not true of JUnit XML.

Why kind is mandatory

Every document must declare "kind": "test-hub-report" or "kind": "test-hub-events". This is not ceremony. A format that claimed “any JSON object with a tests key” would happily swallow a coverage report, ESLint output or half of a package.json, and each of those would arrive as a silently wrong run with a plausible-looking pass rate. Test Hub does not advertise support for arbitrary JSON, so it does not accept it — the refusal mechanics, including the difference between the 415 and the 422 you can get here, are on the adapters page.

Retries

A retry is a new attempt, never a correction. Two equivalent spellings. Nest them:

{
  "name": "keeps the basket after a reload",
  "suite_path": "specs/checkout",
  "attempts": [
    {"status": "failed", "duration_ms": 4100,
     "failure": {"type": "TimeoutError", "message": "locator timed out"}},
    {"status": "passed", "duration_ms": 4300}
  ]
}

or repeat the test with an increasing attempt_number:

{"name": "keeps the basket after a reload", "suite_path": "specs/checkout",
 "attempt_number": 1, "status": "failed"}
{"name": "keeps the basket after a reload", "suite_path": "specs/checkout",
 "attempt_number": 2, "status": "passed"}

Both produce one test with two attempts, because entries are grouped by test identity. The last attempt is the effective outcome, and the disagreement between attempts is what makes the test flaky. Attempt numbers are re-sequenced densely from 1, with an attempt_renumbered warning when the file's own numbering had gaps.

The single most important thing to get right in a publisherReporting a retried test as one row with its final status loses the flakiness entirely. Reporting it as two tests inflates the count and makes the pass rate wrong. Neither mistake produces an error message — both produce a dashboard that is confidently incorrect.

The event stream a report expands into

run.queued → run.started → suite.started* → test.finished* → suite.finished* → run.finished

Every suite is announced before any result arrives, which is what a dashboard subscribing mid-import needs in order to draw the tree before it fills in. If you already speak the event contract, you can send envelopes directly with "kind": "test-hub-events"; sequence numbers are preserved, because they are the file's statement about ordering and the adapter has no better information. A workspace_id that disagrees with the importing workspace is overridden with a warning — a file must never be able to write into another tenant.

Idempotency

Event ids are UUIDv5 over (source, run_id, sequence, type) rather than random, so importing the same file twice against the same run applies zero new events instead of doubling it:

$ test-hub ingest report.json --project storefront-web --run-id a47f1a30-… --json
{"run_id": "a47f1a30-3241-4957-811c-f193b6230654", "created": true,
 "events_applied": 12, "events_ignored": 0,
 "suites_imported": 2, "tests_imported": 4, "attempts_imported": 5}

$ test-hub ingest report.json --project storefront-web --run-id a47f1a30-… --json
{"run_id": "a47f1a30-3241-4957-811c-f193b6230654", "created": false,
 "events_applied": 0, "events_ignored": 12,
 "suites_imported": 0, "tests_imported": 0, "attempts_imported": 0}

Without a run id you get a new run each time, which is correct: two genuine executions of the same suite are two runs. The flip side of derived event ids is worth stating — two different files imported into one run id collide on those ids and lose events. One file, one run.

Generating the JSON Schema

The models are the source of truth and the JSON Schema is generated from them, so there is no second artefact to keep in step. Every model's docstring becomes the description, which means the generated schema carries the same reasoning this page does.

$ python -c "import json; from test_hub.domain.models import Snapshot; \
    print(len(json.dumps(Snapshot.model_json_schema())))"
32803

Snapshot's schema pulls in 25 definitions and is about 33 KB of JSON.

Ask for the serialization schema when you are describing a responsePydantic's default is the validation schema, which omits computed fields. That is correct for “what may I send” and wrong for “what will I receive”.
>>> list(RunCounts.model_json_schema(mode="validation")["properties"])[-3:]
['queued', 'flaky', 'retried']
>>> list(RunCounts.model_json_schema(mode="serialization")["properties"])[-4:]
['completed', 'executed', 'pass_rate', 'failure_rate']

The OpenAPI document at /api/openapi.json is generated by FastAPI from the same models, and is the machine-readable form of the REST contract.
