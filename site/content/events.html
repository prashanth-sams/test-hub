A JUnit XML file dropped on the CLI, a POST /api/v1/imports from a Jenkins job and a live publisher streaming results as they happen all converge on the same list of events and the same apply_events call. Nothing else in the codebase writes a run, a test or an attempt. That is what makes reposting safe, what makes a retry a fact rather than an overwrite, and what makes the counts recomputable from the log at any time.

The types are declared and validated in src/test_hub/domain/events.py, so everything below is enforced at the boundary rather than merely documented. A publisher in any language only has to produce this JSON.

The envelope

The outer shape is CloudEvents 1.0 in structured JSON mode — the seven core attributes — plus four Test Hub extension attributes and the typed data payload.

Why workspaceid and not workspace_id

CloudEvents requires extension attribute names to be made of lowercase letters and digits only — no underscores. That is why the field names, and therefore what goes out on the wire, are workspaceid, runid and schemaversion. sequence was already legal and is spelled the same either way.

Writing those by hand is unpleasant, so the readable spellings are accepted on input. workspace_id, run_id and schema_version are Pydantic validation aliases: either form parses, and only the lowercase form is ever emitted.

Python code never has to type the ugly form either: event.workspace_id, event.run_id and event.schema_version are read-only properties over the extension fields. The one place the raw spelling matters is when you are writing JSON for a language that has no such helper — and there, either spelling works.

Aliases, not synonymsThe aliases are accepted, not preserved. If you round-trip an event through Test Hub and compare it byte for byte with what you sent, the extension keys will have changed spelling. Compare on (source, id) instead — that is the pair the store treats as identity.

Unknown fields are refused, and so is an unknown version

DomainEvent is extra="forbid", and so is every payload model. A publisher that sends durationMs instead of duration_ms gets a 422 naming the field, rather than a silently dropped value and a wrong duration on the dashboard:

This is the single most useful property of the contract during a first integration, and it is worth not loosening. The cost is real and worth stating: a publisher written against a future Test Hub that adds a field cannot send that field to an older server. That is the trade — a loud failure on the new field instead of a quiet loss of it.

A schemaversion this build does not speak is refused for the same reason:

  Value error, unsupported schema_version 2; this build speaks 1
  [type=value_error, input_value=2, input_type=int]

An older Test Hub reading a newer event cannot know which fields changed meaning. A failed import is recoverable by re-running the step; a wrong pass rate that nobody questions is not. Two more envelope-level rejections worth knowing, both real: "time": "2026-09-08T01:15:00" (no offset) gives Input should have timezone info, and "sequence": -1 gives Input should be greater than or equal to 0.

Sequence numbers

sequence is a monotonically increasing integer within one run, assigned by the publisher. It is not global, it is not a timestamp, and it does not have to be dense.

It exists for two jobs. A consumer uses it to notice a gap — a batch that never arrived leaves a hole. The server uses it to apply out-of-order arrivals deterministically: apply_events sorts the batch by (sequence, time) before dispatching, so a batch shuffled by a proxy or a thread pool lands in the order the publisher meant.

sequence is ge=0, and 0 has a special meaning on the way in: server, allocate one for me. RunService._assign_sequences fills the zeros from the run's current high-water mark, inside the same transaction that applies the batch, so two publishers posting concurrently receive disjoint blocks rather than both starting at 1.

if all(event.sequence > 0 for event in events):
    return events                              # nothing to do
cursor = uow.events.next_sequence(run_id)      # max(sequence) + 1, or 1
for event in events:
    if event.sequence > 0:
        keep the publisher's number
    else:
        assign cursor; cursor += 1

Read that carefully, because it means a batch that mixes zeros with real numbers keeps both. The publisher's numbers are honoured and the zeros are allocated from the high-water mark, and nothing checks that the two ranges do not overlap. Here is that happening — four events posted to a fresh run (whose run.queued and run.started already took 1 and 2) with sequences 3, 0, 4, 0:

  sequence 1  run.queued
  sequence 2  run.started
  sequence 3  test.finished    a      <- the publisher's own 3
  sequence 3  test.finished    b      <- allocated from the high-water mark
  sequence 4  test.finished    c      <- the publisher's own 4
  sequence 4  test.finished    d      <- allocated

Nothing is corrupted by that: sequence is not unique, and the fold is keyed on (run, test, attempt_number), so the counts are right. What you lose is the log's readability and any hope of gap detection.

Pick one and stick to itSend all zeros or all real numbers. If you want gap detection — and a suite streaming for an hour is exactly where a silently dropped batch matters — number your own events, because a consumer cannot notice a hole in a sequence the server invented.

EventRepository.list_events(run_id, after_sequence=0) replays a run's log oldest first. after_sequence is exclusive, with one deliberate exception: the default 0 means "from the beginning" rather than "after sequence zero", so a publisher that legitimately numbered its first event 0 does not have it swallowed by the default argument.

Not the same as the SSE cursorThe id: line on the Server-Sent Events stream is a bus cursor: global to the workspace, assigned when the event is published to subscribers, and unrelated to any run's sequence numbers. In a quiet workspace the two happen to line up, which is exactly how people come to rely on it. See the stream section.

Idempotency

Two independent mechanisms at two granularities. You want both, and they answer different questions.

Per event: UNIQUE(source, event_id)

The events table carries UNIQUE(source, event_id). Before applying a batch, SqlEventRepository._existing_keys selects the (source, id) pairs already stored and skips those events, counting them as ignored. Reposting is accepted and is a no-op by construction, not because an endpoint remembered to check. The same set catches duplicates within one batch, so a publisher that appends the same event twice before flushing also gets one row.

id alone cannot be the key. A CloudEvents id is only required to be unique within its source, so two publishers are both entitled to call their first event 1. DomainEvent.dedupe_key() renders the pair as f"{source}\x1f{id}" — a unit separator, because it cannot occur in either half.

The canonical-JSON and JUnit adapters lean on this deliberately. They derive event ids as uuid5(TEST_HUB_NAMESPACE, f"{source}\x1f{run_id}\x1f{sequence}\x1f{type}") rather than randomly, so importing the same file twice against the same run applies zero events:

$ test-hub ingest tests/fixtures/canonical/report.json --project checkout-service --json
  "created": true,   "events_applied": 18, "events_ignored": 0,
  "suites_imported": 3, "tests_imported": 6, "attempts_imported": 9

  "created": false,  "events_applied": 0,  "events_ignored": 18,
  "suites_imported": 0, "tests_imported": 0, "attempts_imported": 0

Eighteen events ignored, nothing imported, same run, and the counts did not move.

The qualifier mattersA report with no run.id gets a fresh random run id on every import, therefore fresh event ids, therefore a second run. If you want repeatable imports, put a stable id in the run block or pass --run-id.

Per batch: X-Idempotency-Key

POST /api/v1/runs/{id}/events and POST /api/v1/imports both accept an X-Idempotency-Key header. The first request stores the key with a summary of what it did; a later request carrying the same key short-circuits before doing any work and returns applied: 0 with ignored equal to the size of the batch it was handed.

$ curl -sX POST "$HUB/api/v1/runs/$RUN/events" \
    -H 'content-type: application/json' \
    -H 'X-Idempotency-Key: doc-batch-1' \
    -d @events.json
{"applied":5,"ignored":0,"created_run":false,"counts":{"total":1,…,"flaky":1,"retried":1,
  "completed":1,"executed":1,"pass_rate":100.0,"failure_rate":0.0},"status":"running"}

{"applied":0,"ignored":5,…}      # replayed from the stored key, no work done

{"applied":0,"ignored":5,…}      # no key: the per-event UNIQUE caught all five

Those last two lines look identical and are not. The keyed call short-circuits on a single primary-key lookup in idempotency_keys and never sorts or dispatches anything; the unkeyed one sorts the batch, queries for the five existing (source, id) pairs, and only then discovers it has nothing to do. For a retried CI step you want the key: it returns the original answer instead of redoing the work, and — crucially — instead of returning "0 applied" for a reason the caller could read as a failure.

Trap: the key is global, not scoped to a runThe idempotency_keys table has key as its primary key, with no workspace and no run in it. Posting a different batch to a different run under a key that has been used before silently discards the batch.
run1 batch A (X-Idempotency-Key: pipeline-42-batch-1)  ->  applied 5  ignored 0
run2 batch B (X-Idempotency-Key: pipeline-42-batch-1)  ->  applied 0  ignored 5

$ curl -s "$HUB/api/v1/runs/$run2" | jq .counts.total
0

The reply to the second call even echoes run_id of run2 — the route builds the response from the URL and then reads that run's counts — so it reads as a normal, successful replay for the run you addressed, while run 2 has nothing in it. Derive the key from something unique per batch, the pipeline id plus a batch number, rather than reusing a constant like batch-1 across jobs.

Opening a run needs no key at all. POST /api/v1/runs with a run_id you chose returns the existing run unchanged — same id, same created_at — instead of erroring, so a retried "announce the run" step is safe on its own terms.

The eight event types

The set is closed. Adding one is a wire-contract change and needs a SCHEMA_VERSION bump, because dashboards and adapters both switch on it.

run.queued → run.started → suite.started* → test.started? → test.finished*
           → suite.finished* → artifact.published* → run.finished

Only test.finished is genuinely load-bearing. A publisher that emits nothing but run.queued, a stream of test.finished and run.finished produces a complete, correct run. Everything else buys you fidelity: a suite tree, a live "running" indicator, attached files.

Every JSON example below is a real frame captured from GET /api/v1/events/stream during the worked run at the bottom of this page, with only the SSE wrapper removed and whitespace added.

Batches

EventBatch — the body of POST /api/v1/runs/{id}/events — is {"events": [...]} with between 1 and 5000 events, all belonging to the same run. The API additionally checks that every event's runid matches the run id in the URL and that every workspaceid matches the server's workspace, so a file cannot write into another tenant and a copy-pasted URL cannot silently scatter events across runs.

A batch is applied atomically: it lands entirely or not at all, so a partially applied batch can never leave the counts half-updated. The whole batch runs inside one SqlUnitOfWork, and _refold rewrites the run's derived numbers once at the end rather than incrementally. That is a deliberate cost — recomputing is more work than adding one to a counter — bought for a specific reason: incremental counters drift, and an event applied twice or a shard arriving out of order leaves them wrong in a way nobody notices until two pages disagree.

The ceiling is Settings.max_events_per_batch (default 5000) as well as the model's own max_length. Exceeding it is a validation_error, not a truncation — losing the tail of a batch quietly would be the worst of both.

Reading the stream back over SSE

Events go out to subscribers on GET /api/v1/events/stream as Server-Sent Events. The transport is SSE rather than WebSockets because the traffic is entirely one-way, and SSE gives three things for free that would otherwise have to be built: automatic reconnection in the browser, Last-Event-ID replay, and passage through any HTTP proxy with no upgrade handshake.

retry: 15000

event: hello
id: 0
data: {"workspace_id":"b037a4b3-53f8-5326-a5d5-f5fad3c31052","replaying":false}

event: test-hub
id: 3
data: {"event":{"specversion":"1.0","id":"cccccccc-0000-4000-8000-000000000001",
       "source":"urn:test-hub:ci","type":"suite.started", … },
       "received_at":"2026-09-09T03:28:54.321659+00:00"}

: heartbeat

The retry: line is sent once, up front, so that a server restart does not produce a reconnect storm. The heartbeat is a comment, emitted every sse_heartbeat_seconds (default 15). There is a fourth frame, which you will not see on a healthy connection:

event: resync
id: 43
data: {"reason":"cursor_expired","oldest_available":1204}

Four things are worth knowing before you write a client.

  • id: is a bus cursor, not the CloudEvent's id. A replayed event keeps its own identity, so using that as the resume token would make resumption ambiguous. Send the last id: you saw back as Last-Event-ID; the browser's EventSource does this for you.
  • It is not the run's sequence either. The bus cursor is global to the workspace and counts every event from every run. In the worked run below the two columns line up exactly, 1 through 9 — because that workspace had no other traffic. On a busy server they will not, and a client that assumed otherwise breaks the first time two pipelines overlap.
  • A heartbeat is a comment and never moves your cursor. It exists to stop proxies closing an idle connection; it carries no id:.
  • resync means refetch, not reconnect. The bus keeps a bounded ring buffer per workspace (sse_replay_buffer, default 1000 events). A client that reconnects inside the buffer is replayed; one that has been away longer, or one too slow to drain its queue, is told to refetch over REST. Silently skipping the gap would leave a dashboard confidently displaying stale numbers, which is worse than a reload.

A full run, end to end

Everything below was executed against a local server on port 8931 with TEST_HUB_DATA_DIR pointed at a scratch directory. The ids are the real ones.

  1. Open the run

    -d '{"project_key":"storefront-web","test_type":"e2e","team":"payments",

  | jq -r .id)

Events in a file

A publisher that already speaks this contract does not need an HTTP session at all. Put the raw stream in a file and import it:

{"kind": "test-hub-events", "schema_version": 1, "events": [ …CloudEvents envelopes… ]}
$ test-hub ingest events.json --project ledger-worker --json
  "adapter": "testhub-json", "created": true,
  "events_applied": 7, "events_ignored": 0,
  "tests_imported": 2, "attempts_imported": 2,
  "counts": {"total": 2, "passed": 1, "failed": 1, "completed": 2, "executed": 2,
             "pass_rate": 50.0, "failure_rate": 50.0}

The testhub-json adapter validates each envelope and passes it through unchanged, preserving sequence numbers — they are the file's own statement about ordering and the adapter has no better information. Missing run_id, workspace_id and source are filled in from the import request.

A workspace_id that disagrees with the importing workspace is overridden rather than honoured, because a file must never be able to write into another tenant. It is overridden loudly:

  "code": "workspace_override",
  "message": "7 event(s) named a different workspace; they were re-homed into
              the importing workspace",
  "severity": "warning"
