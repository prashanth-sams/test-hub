The shape of the command line

Every command takes -h or --help, and the root command takes -V/--version. The version line reports two numbers, because they move independently: the package version, and the canonical schema version that every payload carries.

$ test-hub --version
test-hub 0.1.0 (canonical schema v1)
  serve    Start the API and serve the dashboard.
  ingest   Import a report file into the local store.
  publish  Send a report to a remote Test Hub server.
  demo     Populate the store with realistic sample data.
  prune    Delete runs older than a retention cutoff.
  formats  List the installed report adapters.
  token    Create and hash API tokens.

Sub-commands are registered lazily, inside a function, so test-hub --help does not import FastAPI, SQLAlchemy and every adapter to print seven lines. That is the difference between a help screen that feels instant and one that does not, and it is the reason each command imports its own service module in its first line of body rather than at module scope.

ingest and publish take --json, and print the very object the human summary was rendered from — ImportResult.model_dump(mode="json") — rather than a second formatter that could drift away from it. So a CI step parses exactly what the terminal described. formats --json does the same for the adapter registry.

There is no --token flag, on purpose

Neither publish nor token hash will take a token as an argument. This is not an oversight to be worked around; it is the one rule that shows up in every command that touches a credential.

  • ps is world-readable. On a shared build agent, every other user on the box can read the full argument vector of every running process. A token on a command line is a token handed to anyone with a shell on that machine.
  • Shell history keeps it. ~/.bash_history and ~/.zsh_history are written on exit, are rarely encrypted, and are frequently backed up.
  • CI logs echo commands. Most runners print the command before running it, and those logs are often readable by more people than the secret store is.

The two supported ways in:

OptionDefaultBehaviour
--token-env NAMETEST_HUB_TOKEN Reads $NAME and strips whitespace. If you name a variable explicitly and it is unset or empty, that is an error. If you leave the default and TEST_HUB_TOKEN happens to be unset, the publish goes ahead unauthenticated — which is the normal case against a local, unauthenticated server.
--token-file PATH— Reads the file and strips whitespace. A missing or empty file is always an error. This is the form for Docker/Kubernetes secrets and for GitLab's file-type variables.

--token-file wins if you pass both; it is checked first and returns before the environment is consulted.

$ test-hub publish results.xml --project p --url http://127.0.0.1:8811 --token-env MY_MISSING_VAR
error: environment variable MY_MISSING_VAR is not set or is empty; export it before running, or use --token-file
# exit 78

$ test-hub publish results.xml --project p --url http://127.0.0.1:8811 --token-file /tmp/empty.token
error: token file /tmp/empty.token is empty
# exit 78
TipIf you must inline a token in a one-off command, do it through the environment of that single command — TEST_HUB_TOKEN="$SECRET" test-hub publish … — rather than through a flag. The value still reaches the process, but it never appears in the argument vector that ps shows.

The warning appears twice because it is raised in two places: by the CLI before it binds, and by the application at startup. The second one is the one that matters if you skip the CLI — run create_app under your own ASGI server, or use --reload, where the app is built in a subprocess on every restart, and the CLI's copy is printed once or not at all.

The environment does not reach these flags--host, --port and --log-level always send a value to the settings overlay, including their defaults, and a supplied value beats the environment. So TEST_HUB_HOST=0.0.0.0 TEST_HUB_PORT=9999 test-hub serve binds 127.0.0.1:8000 — verified, not theoretical. Pass the flags. Only --data-dir declares an environment variable, and TEST_HUB_INSECURE_NO_AUTH works because the flag maps its False to "unset". More on that on the configuration page.
About --reloadIt watches the directory the package was imported from — the checkout's src/ if you installed with pip install -e, and site-packages if you installed a wheel. In the second case it will restart on any change to any installed package, which is not what you wanted. It is a development flag.

That counts_mismatch is the file being caught in a small lie: its <testsuite> element declares tests="5" while the element actually contains six <testcase> children. Test Hub keeps what it parsed and says so, rather than trusting an attribute that the writer computed separately from the cases. Warnings are printed ten at a time, then summarised as … and N more, so a pathological file cannot flood the terminal.

Re-importing the same file

Pass --run-id and the second import applies nothing. Event ids for the canonical JSON adapter are a UUIDv5 over (source, run_id, sequence, type), and (source, event id) is unique in the store, so the events are recognised as already applied:

  updated run a7be9e5c-4e76-4341-890f-ba7538fc2b40
  adapter   junit-xml (detected, 90% confident)
  project   payments-api
  stored in /private/tmp/th-site-cli
  6 tests  3 passed  1 failed  1 error  1 skipped  1 flaky  60.0% pass
  12 event(s) had already been applied and were ignored

Note updated rather than imported, and that the counts did not move. Without --run-id you get a new run every time, which is the right default — re-running a suite is a new run, not a correction to the old one.

Forcing an adapter that cannot cope produces the adapter's own complaint, also exit 2 — error: this file is not well-formed XML: syntax error: line 1, column 0. Naming an adapter that is not installed produces error: unknown format 'nope' followed by the same installed-adapter list. In all three cases the list of what is supported travels with the error, and it is the same list the HTTP API returns in its 415.

publish

The same import against somebody else's server. Same adapters, same parsing, same ImportResult — the work happens on the server, and this command is an HTTP client around POST /api/v1/imports. Everything it does is something curl could do; that is a design constraint on the API, not a coincidence.

It takes every option ingest takes, minus --data-dir, plus:

OptionDefaultWhat it does
--urlhttp://127.0.0.1:8000Base URL of the server. Also reads TEST_HUB_URL.
--token-envTEST_HUB_TOKENName of the variable holding the token. See above.
--token-file—File holding the token.
--timeout60.0Seconds, per request.
--insecureoffSkip TLS certificate verification. Only for a server with a private CA you have not installed yet.
--idempotency-key—Sent as X-Idempotency-Key. A retried publish under the same key is a no-op instead of a duplicate run.
--triggerunknownDiffers from ingest, whose default is local. A publish usually comes from a pipeline, and claiming it was local would be a lie.
 
$ export TEST_HUB_TOKEN='ths_…'        # from `test-hub token create`
$ test-hub publish results.xml \
    --url http://127.0.0.1:8811 \
    --project payments-api \
    --team payments \
    --type integration \
    --branch "$GIT_BRANCH" \
    --commit "$GIT_COMMIT" \
    --token-env TEST_HUB_TOKEN
  imported run 2dbda2c1-f23b-4d9f-9824-2f2788fa1490
  adapter   junit-xml (detected, 90% confident)
  project   payments-api
  stored in http://127.0.0.1:8811
  6 tests  3 passed  1 failed  1 error  1 skipped  1 flaky  60.0% pass

The only difference from the ingest output is the stored in line, which names the server instead of a directory. The client retries a connection error and the statuses that are worth retrying — 408, 425, 429, 500, 502, 503 and 504 — up to three times, with a backoff between attempts. Every other 4xx is returned immediately, because a malformed request will be exactly as malformed on the second attempt. Retries reuse the same X-Idempotency-Key, so a timeout that had actually succeeded server-side does not produce a second run.

Server-side failures surface as exit 1A rejected token, an unreachable host or a 5xx comes back as TestHubClientError, which is a RuntimeError rather than one of Test Hub's own error classes — so it escapes the CLI's error handler and prints a Python traceback with exit code 1, not the exit 5 the taxonomy would suggest. The message on the last line is accurate (a valid bearer token is required; send it as `Authorization: Bearer <token>` or `X-API-Key: <token>`); the presentation is not. Branch on 0-vs-non-zero for publish, not on the specific code.

You do not need Test Hub installed on the build agent at all. The equivalent curl, with the same authentication, is on the getting started page.

token

Two sub-commands, both of which exist because Test Hub stores only PBKDF2 digests. Nothing on the server can recover a token; the plaintext exists in exactly one place, for as long as your terminal scrollback keeps it.

token create

OptionDefaultWhat it does
--labelciA note for your own records. It appears in a comment in the printed snippet and is not stored anywhere — the server never sees it.
 
  Token (shown once — copy it now)
  ths_Itl-rN2xWt77MMFWbio3kn8OqyNelvebooRMFnD6p2E

  Configure the server with the hash, not the token:
  export TEST_HUB_API_TOKEN_HASHES="pbkdf2_sha256$120000$2c78b65c9fb65300c908c68af1250978$7a9b282ed5a62cdfe0a53dfba669a5967131fb58c160e5f92bbc961ba1a22b85"

  Publishers use the token itself:
  export TEST_HUB_TOKEN="ths_Itl-rN2xWt77MMFWbio3kn8OqyNelvebooRMFnD6p2E"   # label: ci-github
  test-hub publish results.xml --url https://… --project p --token-env TEST_HUB_TOKEN

  Test Hub keeps only the hash. Nothing can recover this token from the server.

The token is 256 bits of secrets.token_urlsafe behind a ths_ prefix. The prefix costs four characters and buys two things: secret scanners can be taught to recognise it, and a human reading a log can tell what they are looking at.

Do not paste that hash line into a shell as printedIt is printed inside double quotes, and a PBKDF2 hash contains four $ characters. In bash or zsh, "…$120000$…" expands $1, $5 and $0 before the variable is ever set. The line above, pasted verbatim into zsh, produced pbkdf2_sha256f46ca…/bin/zshdd92bd… — the server then rejects every token and tells you the token is wrong, which sends you looking in the wrong place. Retype the quotes as single quotes, or write the value into a file. There is more on this, including the docker-compose variant, on the configuration page.

token hash

Hashes a token you already have — for rotating a server's configuration without reissuing a token to every publisher, or for hashing a token that came out of a password manager.

OptionDefaultWhat it does
--token-envTEST_HUB_TOKENName of the environment variable holding the token to hash. There is no argument form, for the same reason publish has none.
 
$ TEST_HUB_TOKEN='ths_…' test-hub token hash
pbkdf2_sha256$120000$84cf00d22b1abb3857b796badcfb460d$266c36495c2a60ff1ebc6d6c67821e9bcfd60e231d8390bde1914c659541cee3

Four $-separated fields: algorithm, iteration count, salt hex, digest hex. The salt is random per call, so hashing the same token twice gives two different lines and both verify. Unlike every other failure on this page, an unset variable here exits 2 through Typer rather than through the error taxonomy:

  environment variable TEST_HUB_TOKEN is not set or is empty
# exit 2

Exit codes

Every deliberate failure in Test Hub is one of a small set of error classes, and each class carries both an HTTP status and an exit code. They are mapped to HTTP in one place and to an exit code in one place, so test-hub ingest and POST /api/v1/imports disagree about nothing except the transport. A CI step can therefore branch on why it failed rather than only on the fact that it did.

ExitError classerror codeHTTPMeans
0———Success.
1TestHubErrortest_hub_error500 The base class, and also where anything unanticipated lands — including a failed publish and an invalid setting value.
2ValidationErrorvalidation_error422 Well-formed input that said something impossible. Typer's own usage errors (a missing --project, a file that does not exist) also exit 2.
2AdapterErroradapter_error422 An adapter claimed the input and then could not parse it.
2UnknownFormatErrorunknown_format415 No installed adapter recognised the input. Carries the installed-adapter list.
3NotFoundErrornot_found404 A run, test or artifact that does not exist. Reached over HTTP; the local CLI commands create what they need rather than failing.
4ConflictErrorconflict409 A write contradicted a write that already landed.
5AuthenticationErrorunauthorized401 No token, or a token that does not verify.
5AuthorizationErrorforbidden403 A valid token that is not allowed to do this.
6PayloadTooLargeErrorpayload_too_large413 A report, an artifact or a decompressed upload past its configured ceiling.
78ConfigurationErrorconfiguration_error500 EX_CONFIG. Test Hub was asked to start, or to run, in a state that is not safe or not coherent.
130———Ctrl-C. Prints interrupted and stops.

78 is EX_CONFIG from sysexits.h, chosen so a supervisor — systemd, Kubernetes, a Compose healthcheck — can tell "you configured this wrong" apart from "it crashed" and stop restarting something that will never come up.

$ TEST_HUB_MAX_REPORT_BYTES=1024 test-hub ingest results.xml --project payments-api
error: report exceeds the 1024 byte limit (TEST_HUB_MAX_REPORT_BYTES); split the upload or raise the limit
  limit_bytes: 1024

$ echo $?
6

Structured detail is printed under the message, one key: value per line, on stderr along with the message itself. Standard output stays clean, so --json piped into jq is not polluted by an error.

Two honest gapsCodes 3, 4 and 5 are defined and are what the HTTP API returns, but the CLI does not currently reach them: the SDK client raises its own TestHubClientError, which is not part of the taxonomy, so an authentication failure during publish exits 1 with a traceback. Likewise an invalid value for a TEST_HUB_* variable surfaces as a Pydantic ValidationError traceback and exit 1 rather than exit 78. Both were verified against 0.1.0.
