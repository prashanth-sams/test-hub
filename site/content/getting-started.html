Install it

Test Hub is one Python package. It needs Python 3.11 or newer and nothing else — no Node, no database server, no container runtime. The dashboard is hand-written CSS and JavaScript shipped inside the wheel, so there is no build step to run and nothing to fetch from a CDN.

$ pip install test-hub

That gives you the test-hub command, the test_hub import package and the Python publishing SDK. Storage is SQLite in a file, artifacts are a directory of files, and both are created on first use.

See it with data in it

An empty dashboard tells you nothing about whether you want one. test-hub demo invents a plausible organization — five projects across three teams, two weeks of history, real failures, genuinely flaky tests, and one run that is still going so the live indicator has something to show.

  1. Seed the sample data

    $ test-hub demo

    It prints what it made:

      seeding sample data…

  sample data created
  5 projects, 31 runs, 258 test results, 270 attempts
  23 failures and 12 flaky retries, so the red and amber states have something to show
  one run is still open: f0c9dd0b-4534-4e9c-8ede-844121dd118b
  stored in /private/tmp/th-docs-site

  next:  test-hub serve

  2. Start the server

    $ test-hub serve
      Test Hub  http://127.0.0.1:8000
  dashboard http://127.0.0.1:8000/
  API docs  http://127.0.0.1:8000/api/docs
  data      /Users/you/Library/Application Support/test-hub

    It binds loopback. Nothing else on the network can reach it, which is why it does not ask you for a token yet. Opening it up is a separate, deliberate step — see Security.

  3. Open the dashboard

    http://127.0.0.1:8000/. The dashboard tour walks through what every panel means; the short version is Overview for "how is the portfolio doing", Runs for finding one, and the run and test pages for "why did this go red".

TipPoint TEST_HUB_DATA_DIR at a scratch directory while you are experimenting, and the demo data never touches the store you keep. Everything below in this page was produced with TEST_HUB_DATA_DIR=/tmp/th-docs-site.

Import a report you already have

If anything in your build writes JUnit XML — pytest with --junitxml, Maven Surefire, Gradle, Jest, Playwright, Go's gotestsum, .NET through a converter — you already have an input. ingest parses it into the local store.

$ test-hub ingest results.xml \
    --project payments-api \
    --team payments \
    --component checkout \
    --environment staging \
    --type component
  imported run 5c45c0b4-bdb1-4686-828f-cb3149216918
  adapter   junit-xml (detected, 90% confident)
  project   payments-api
  stored in /private/tmp/th-docs-site
  5 tests  2 passed  1 failed  1 error  1 skipped  1 flaky  50.0% pass

  1 parser warning(s):
    naive_timestamp [testsuite[CheckoutIT]]: timestamps in this report carry no UTC offset; they are read as UTC

Three things in that output are worth reading rather than skimming.

  • The adapter, and how confident detection was. Nothing guessed silently. A <testsuites> root scores 0.9; a file that declares "kind": "test-hub-report" scores 1.0. If detection picks wrong, --format junit-xml overrules it — see Adapters.
  • The counts are folded, not copied. The file's own tests="5" failures="1" attributes were advisory. Test Hub counted the cases it actually parsed. Where the two disagree you get a counts_mismatch warning instead of a wrong number.
  • Five tests, six attempts, one flaky. The file had a Surefire <flakyFailure> in it: a test that failed and then passed on a rerun. Test Hub stores both attempts, counts the test once through its last one, and flags it flaky. How that is defined.
NoteEvery flag above except --project is optional, and every one of them is worth setting. They are what the filters filter on, and — with the exception of --project — they are also what makes a run comparable to the previous one. A run with no environment and no branch is compared against other runs with no environment and no branch.

Publish from CI to a shared server

The same import, aimed at a server somebody else is running. publish is ingest over HTTP: same adapters, same parsing, same result object.

$ export TEST_HUB_TOKEN='ths_…'          # from `test-hub token create`
$ test-hub publish results.xml \
    --url https://test-hub.internal \
    --project payments-api \
    --team payments \
    --type component \
    --branch "$GIT_BRANCH" \
    --commit "$GIT_COMMIT" \
    --token-env TEST_HUB_TOKEN

There is deliberately no --token flag. A token on a command line is visible in ps to every other user on the machine, lands in shell history, and appears in the CI log whenever a step is echoed. --token-env and --token-file are the two supported ways in.

You do not need Test Hub installed on the build agent at all. This is a complete publisher:

curl -X POST https://test-hub.internal/api/v1/imports \
  -H "Authorization: Bearer $TEST_HUB_TOKEN" \
  -F "file=@target/surefire-reports/TEST-com.example.LedgerTest.xml" \
  -F "project=ledger-worker" \
  -F "team=payments" \
  -F "type=integration" \
  -F "environment=staging" \
  -F "branch=$GIT_BRANCH" \
  -F "commit=$GIT_COMMIT"

Worked pipelines for GitHub Actions, GitLab CI, Jenkins and friends are on the CI integrations page.

Where the data lives

By default, in the platform's user-data directory — not in whatever folder you happened to be standing in, so that test-hub serve run from two different projects is one Test Hub rather than two.

PlatformDefault data directory
macOS~/Library/Application Support/test-hub
Linux$XDG_DATA_HOME/test-hub, or ~/.local/share/test-hub
Windows%LOCALAPPDATA%\test-hub

Inside it: test-hub.db (SQLite, in WAL mode) and artifacts/ (content-addressed files). The directory is created with mode 0700 where the filesystem supports it. Override it with --data-dir or TEST_HUB_DATA_DIR, both of which mean the same thing.

$ export TEST_HUB_DATA_DIR=/tmp/th-scratch
$ test-hub demo --reset
$ test-hub serve
